1. The project in one page

The problem

Colleges have many students doing coding contests, internships, certificates and open-source work. Today this proof is scattered and nobody can compare students fairly. GEHU Forge is a C++ program that collects each student's achievements, lets them be verified (approved or rejected), turns approved ones into a score called EXP, and keeps a live ranking (leaderboard) of students.

Why no STL?

STL (Standard Template Library) is C++'s ready-made toolbox: vector, map, queue and so on. This is a Data Structures and Algorithms (DSA) project, so using the toolbox would hide the very thing we must show. Rule of the project: no STL containers. We build our own. (std::string, iostream, fstream, cmath are still allowed. STL is used only inside tests, as an independent checker.)

The five custom structures

LinkedQueue<T>ManyaFirst-come-first-served line for pending verifications

What the program does

  • It has 100 synthetic (fake, computer-generated) students and their achievements, stored in two CSV files (plain text tables: data/students.csv and data/achievements.csv). If the files are missing, they are generated.
  • A CLI (command-line menu) lets you add students, submit achievements, review pending ones, and show the Top 10 leaderboard.
  • Saksham's part is the foundation: the three structures everyone else stores data in, plus loading, saving and generating the data.
Your one-sentence pitch"I built the base layer: our own growable array, hash map and hash set, and the DataStore that owns every object and reads and writes the CSV files, plus the generator that makes 100 reproducible students, and tests that check my structures against the STL."

2. System architecture and flow

Yellow/orange boxes are Saksham's parts. Everything else depends on them, because every lookup by id goes through his HashMap.

The flow, step by step (from the design spec)

  1. Load. DataStore::loadFromCsv() reads the two CSV files (Saksham). If the files are missing, DataGenerator makes the data.
  2. Own. DataStore owns the objects, held in HashMap<int,Student*> and HashMap<int,Achievement*>.
  3. Submit. In the CLI, "Submit achievement" validates input and builds an Achievement object with status Pending (Divyanshi builds, Manya's class).
  4. Queue. VerificationService::submit(a) puts the achievement's id into a LinkedQueue<int> (first-in, first-out).
  5. Review. "Review next" calls reviewNext(registry, approve). It finds the achievement in the HashMap, then calls approve() or reject().
  6. Score. RankEngine::applyAchievement(student, ach) (Pranjal) uses a score-once guard tryConsumeForScoring(), then: weighted points = base × categoryWeight × platformMultiplier × dailyDecay; raw score goes through log normalisation to EXP (0..10000).
  7. Update. The HashMap is updated in O(1) and the AVLTree does erase + insert in O(log N).
  8. Show. The leaderboard gives getTopK(10) in O(K + log N) and getRank(id) in O(log N). The CLI prints the leaderboard or profile card.

3.1 DynArray<T> – a growable array

File: ds/DynArray.h. What it is: an array that grows by itself when it gets full. It is our own version of std::vector.

Public API (from the spec)

MethodMeaningCost
DynArray()make empty arrayO(1)

operator=(const DynArray&)copy assignmentO(n)

Concept A: dynamic memory (new / delete[])

(a) Definition. Normal local variables live on the stack and have a fixed size decided at compile time. Dynamic memory lives on the heap: you ask for it while the program runs (new T[n]) and you must give it back (delete[]). Analogy: renting a storage room; you must return the key.

(b) How it works. DynArray keeps a pointer to a heap block, a size (items used) and a capacity (room available). When full, it asks for a bigger block, copies, and frees the old one:

(c) Where. ds/DynArray.h, inside push_back (grow step) and the destructor (delete[]). DynArray is used everywhere: DataStore::studentOrder, achievementOrder, AVLTree::topK output, Student::achievements, splitLine output.

(d) Why this and not a plain fixed array? We do not know how many students or achievements there will be (the user can add more at any time). A fixed array wastes space or overflows. A linked list would not give O(1) [i].

(e) Complexity. Index O(1). push_back amortised O(1), but one single push can cost O(n) (the copy). Space O(n); up to about half is spare at worst (because of doubling).

Concept B: amortised O(1) and why doubling (not +1)

(a) Amortised means "average cost per operation over a long sequence, even if a few operations are expensive". Analogy: you pay a big yearly fee, but spread over 12 months it is small per month.

(b) Insert 16 items starting at capacity 4. Copies happen when going 4→8 (copy 4), 8→16 (copy 8) = 12 copies plus 16 writes. Total about 28 steps for 16 items, under 2 per item. In general: copies = 4 + 8 + 16 + ... + n/2 < n, so total work is under 2n, which is O(1) per push.

Growing by +1 instead: every push after full copies everything: 1 + 2 + 3 + ... + n = about n²/2 steps, which is O(n) per push, far worse.

(c) DynArray::push_back. (d) Doubling gives geometric growth; +1 or "+10" is still O(n) average. (e) Amortised O(1); worst single push O(n).

Concept C: templates

(a) A template is a blueprint for code where the type is a blank: template<class T> class DynArray. The compiler stamps out a real class for each type you use (DynArray<int>, DynArray<std::string>). Analogy: a cookie cutter; one cutter, many cookies.

(b) Writing DynArray<int> a; makes the compiler copy the class and replace T with int. Because of this, template code sits in header files (.h), which is why the structures are in ds/*.h.

(c) DynArray<T>, HashMap<K,V>, HashSet<T>. (d) Without templates we would copy-paste one array class per type (int, string, RankKey, Achievement*...). (e) No runtime cost; it is resolved at compile time (code size grows a little per type).

Concept D: Rule of Three, deep vs shallow copy, RAII, ownership

(a) If a class owns a resource (here heap memory), it needs three special functions: destructor (free it), copy constructor and copy assignment (copy it correctly). This is the Rule of Three. RAII (Resource Acquisition Is Initialisation) means: the object acquires the resource in its constructor and releases it in its destructor, so cleanup is automatic when the object goes out of scope. Ownership means "this object is responsible for freeing that memory".

(b) Shallow copy copies only the pointer: two objects point to the same block. Deep copy makes a new block and copies the items.

(c) DynArray implements all three (deep copy). HashMap implements the destructor and deletes copying. DataStore destructor deletes all objects.

(d) Why not rely on the compiler's default copy? The default is a shallow copy, which causes the double free above. Also copy assignment must handle a = a (self-assignment) and free the old block before taking the new one.

(e) Deep copy is O(n) time and O(n) extra space.

Concept E: = delete

(a) = delete tells the compiler "this function is forbidden". Using it gives a compile error instead of a hidden bug. (b) HashMap(const HashMap&) = delete; and operator=(const HashMap&) = delete; so HashMap b = a; will not compile. (c) ds/HashMap.h (spec: copy constructor/assignment deleted). (d) Why delete and not write a deep copy? A deep copy of a hash map is costly (rebuild every node) and the project never needs it: we pass maps by reference (for example reviewNext(const HashMap<int,Achievement*>& registry, ...)). Forbidding is safer and less code. (e) No runtime cost at all; the check happens at compile time.

Mini API recap you can say aloudDynArray = pointer + size + capacity. Grow by doubling. Rule of Three because it owns memory. Index is O(1); push_back is amortised O(1); removeAt is O(n).

3.2 HashMap<K,V> – key to value in about O(1)

File: ds/HashMap.h. What it is: a "dictionary". You give a key (like a student id) and get the value (the Student pointer). Analogy: a library with numbered shelves; you do not scan all books, you compute the shelf from the book code.

Public API (from the spec)

ItemMeaningCost
unsigned long hashKey(int), hashKey(const std::string&)turn a key into a big number (string: polynomial rolling hash, base 31)O(1) for int; O(length) for string
void put(const K&, const V&)insert or overwriteavg O(1)
V* find(const K&) and const versionpointer to the value, or nullptr if missingavg O(1)
bool contains(const K&) constis the key there?avg O(1)
bool remove(const K&)erase key; true if it existedavg O(1)
int size() const, int bucketCount() const, double loadFactor() constitems / buckets / items÷bucketsO(1)
template<class F> void forEach(F f) constcall f(key, value) for every entryO(buckets + n)
Destructor; copy ctor and assignment = deletefree all chains; forbid copyingdestructor O(n + buckets)

Inside: Node = { K key; V value; Node* next; }. The table is an array of Node* (the buckets). Start capacity: 16 buckets.

Concept F: hashing and the hash function

(a) A hash function turns a key into a number. We then use number % bucketCount to pick a bucket (a slot). Same key always gives the same number. Analogy: a school roll number decides your row in the exam hall.

(b) For strings we use a polynomial rolling hash with base 31: start with 0, and for each character do h = h*31 + character. Example for "ab": 'a' = 97, 'b' = 98. After 'a': 97. After 'b': 97×31 + 98 = 3105. With 16 buckets: 3105 mod 16 = 1, so the key goes to bucket 1. Because each character is multiplied by a different power of 31, "ab" and "ba" give different numbers (so order matters). "ba": 98×31+97 = 3135.

(c) hashKey() overloads in ds/HashMap.h. Used with string keys in RankEngine::dailyCount (key like "studentId|date") and in HashSet<std::string> for skills. (d) Why this? It is cheap, simple, and spreads similar strings. A bad hash (for example "sum of characters") makes "ab" and "ba" collide always. (e) O(L) for a string of length L; O(1) for an int.

Concept G: collisions and separate chaining; what is in a bucket?

(a) A collision is when two different keys land in the same bucket (unavoidable: many keys, few buckets). Separate chaining fixes it: each bucket holds a linked list (chain) of all nodes that landed there. A bucket stores a pointer to the first node of its chain, or nullptr if empty. A linked node is a small box with data and a pointer to the next box.

(b) Teaching example with 4 buckets, int keys, and hash = key (so bucket = key mod 4). Insert 10, 21, 7, 14, 3:

(c) Inside put, find, remove in ds/HashMap.h: compute bucket, then walk the chain comparing keys. Important: the node stores the full key, because different keys share a bucket, so we must compare the real key, not just the hash.

(d) Why chaining, not "move to next empty slot" (open addressing)? Chaining is easier to write and to delete from, and it never "fills up"; it just gets longer chains. (e) Average O(1) if chains are short. Worst case O(n) if all keys land in one bucket (one long chain, effectively a linked list). Space O(buckets + n).

Concept H: load factor and rehashing (0.75)

(a) Load factor = size / bucketCount (average chain length). Rehashing = building a bigger table and re-inserting every node. Rule from the spec: when size/capacity > 0.75, double the bucket count and re-insert every node. Start: 16 buckets.

(b) Why re-insert instead of just copying? The bucket index is hash % bucketCount. When bucketCount changes, a key's bucket changes too, so every node must be placed again. (Full step-by-step trace in section 4.)

(c) A private grow/rehash step called from put in ds/HashMap.h (exact private name is not in the spec). (d) Why 0.75? It is a common balance: lower wastes memory on empty buckets, higher makes chains longer and slower. (e) One rehash is O(n). It is still amortised O(1) per put for the same reason as DynArray: the size doubles each time, so the total rehash work over n puts is about n + n/2 + n/4 ... < 2n.

Concept I: find() returns a pointer, nullptr if missing

(a) V* find(const K&) returns the address of the stored value, or nullptr ("points to nothing") if the key is absent. (b) Example: Student** p = students.find(42); if (p) { Student* s = *p; } (here V is Student*, so find gives a pointer to a pointer). (c) HashMap::find; used by DataStore::findStudent and VerificationService::reviewNext. (d) Why not return a reference or a default value? A reference cannot say "not found". Returning a default value (like 0) cannot tell "missing" from "real 0". A pointer gives three things in one: found / not found, and the ability to modify in place (*p = newValue) without a second lookup. (e) avg O(1). Always check for nullptr before using; dereferencing null crashes.

Concept J: forEach with a callable (template parameter F)

(a) A callable is anything you can call like a function: a function, a lambda (a small unnamed function written inline), or an object with operator(). template<class F> void forEach(F f) const accepts any callable and calls f(key, value) for each entry. (b) Example: map.forEach([&](const int& k, const Student* const& v){ count++; });. (c) HashMap::forEach and HashSet::forEach. (d) Why not hand out the internal buckets / iterator? That exposes the private table and any change to it (like a rehash) breaks the caller. forEach keeps internals hidden. A template parameter, instead of std::function, avoids STL and lets the compiler inline the call. (e) O(bucketCount + n). The order is bucket order, not insertion order; this is why DataStore keeps separate insertion-order arrays.

3.3 HashSet<T> – a set with no duplicates

File: ds/HashSet.h. What it is: a collection where each item appears at most once. The Set ADT (Abstract Data Type = a description of what operations exist, not how they work) offers add, contains, remove.

MethodMeaningCost
bool add(const T&)add; false if already presentavg O(1)
bool contains(const T&) constis it present?avg O(1)
bool remove(const T&)remove; true if it was thereavg O(1)
int size() constnumber of itemsO(1)
template<class F> void forEach(F f) constvisit each itemO(buckets + n)

Concept K: composition (HashSet wraps HashMap<T,bool>)

(a) Composition = a class has a member of another class and uses it, instead of rewriting it (a "has-a" relation, not an "is-a" inheritance). (b) The set keeps a HashMap<T,bool>. The element is the key; the bool value is a dummy (always true). So add(x) means "if the map already contains x return false, otherwise put(x, true) and return true". contains(x) is map.contains(x). (c) ds/HashSet.h. Used as Student::skills (HashSet<std::string>). (d) Why composition, not inheritance, and why not a DynArray? A set "is not a" map; it just uses one. Reuse means any bug fixed in HashMap fixes the set too. A DynArray would need an O(n) scan to check duplicates on every add; the hash set does it in O(1). (e) Space: one dummy bool per element. Also, because the HashMap copy is deleted, HashSet cannot be copied either (the compiler will refuse).

Cost of the choice, in numbersChecking duplicates among n skills: array scan = n comparisons each time; hash set = about 1. For a student with 5 skills it hardly matters, but the design scales and shows the idea.

Concept L: DataStore owns the objects (and its destructor deletes them)

(a) The objects are created with new elsewhere, then handed to the store. The store is the single owner, so only it deletes them. Other classes (for example Student::achievements, VerificationService) hold non-owning pointers: they use but never delete. (b) Destructor: walk the hash maps (or the order arrays) and delete each Student* and Achievement*. Deleting an Achievement* works correctly because the base class has a virtual ~Achievement() (so the real subclass destructor runs). (c) DataStore::~DataStore, clear(). (d) Why one owner? If two places deleted the same pointer: double free. If nobody deleted: memory leak. One clear owner removes both bugs. (e) O(n) to clean up.

Do not mix up the two kinds of ownershipHashMap<int,Student*>'s destructor only frees its nodes, not the Student objects the pointers point to. Freeing the Students is DataStore's job.

Concept M: factory (use of createAchievement)

(a) A factory is a function that builds the right subclass object from a description, so the caller does not need to know the class names. (b) The spec gives Achievement* createAchievement(const std::string& type, id, studentId, title, date, score, proof, platform); it returns nullptr for unknown type. The CSV loader reads the type column ("CODING", "CERT", "OSS", "INTERN") and calls the factory. (c) Defined by Manya in Achievement.h; called by DataStore::loadFromCsv and by DataGenerator (generation uses the same entry point; the spec says the factory is "used by CSV loader and CLI"; see guess list at end). (d) Why? Without it, the loader would need a long if/else that knows every subclass. (e) O(1). Always check for nullptr (a bad CSV row with an unknown type must not crash the loader).

Concept N: file I/O (ifstream / ofstream) and CSV parsing

(a) File I/O = reading/writing files. std::ifstream (input file stream) reads; std::ofstream (output file stream) writes; std::getline(file, line) reads one line. CSV = Comma-Separated Values: one record per line, fields separated by commas. (b) Files:

students.csv      id,name,email,branch,gradYear,github,leetcode,skills      (skills joined with ;)
achievements.csv  id,studentId,type,title,date,score,platform,proof,status

(c) DataStore::loadFromCsv / saveToCsv in Storage.h. (d) Why CSV and not a database or binary file? It is human-readable (open in Notepad/Excel to check), needs no library, and it shows file handling clearly. (e) Time O(total characters). Both load and save return a bool so the caller can tell if the file could not be opened.

Concept O: splitLine and why commas are stripped from free text

(a) splitLine(const std::string& line, char delim, DynArray<std::string>& out) cuts a line at each delimiter and pushes each piece into out. (b) splitLine("7,Asha,asha@x.in", ',', out) gives out = ["7", "Asha", "asha@x.in"]. The same function splits skills on ';'. (c) Helper in Storage.h. (d) Why strip commas? Our splitLine is simple: it does not understand quotes. A title like "Won Round 1, 2" would split into two fields and shift every later column (the score would be read as the platform...). The spec fixes this the cheap way: commas are removed from free text (title, proof) when writing, and the CLI rejects commas on input. The professional alternative is quoted CSV ("a,b") with a real parser; that is more code. (e) O(L). Limitation: text with commas cannot be stored exactly (they are lost).

3.5 DataGenerator – reproducible synthetic data

File: Storage.h. Call: DataGenerator::generate(DataStore&, int studentCount = 100, unsigned seed = 2026). It makes fake names, branches, skills, and 1 to 3 achievements per student. Statuses: about 80% Approved, 12% Pending, 8% Rejected.

Concept P: linear congruential generator (LCG) and fixed seed

(a) A pseudo-random number generator makes numbers that look random but are computed by a formula. An LCG is the simplest: next = (a × current + c) mod m. The first current is the seed. (b) Tiny example (not the project's constants): a=5, c=3, m=16, seed=7: 7 → (35+3) mod 16 = 6 → (30+3) mod 16 = 1 → (5+3) mod 16 = 8 ... Run it again with seed 7: the same sequence every time. To get "80% approved", draw a number 0..99 and treat <80 as Approved, 80..91 as Pending, the rest Rejected (the cut points are an illustration; the spec only gives the percentages). (c) DataGenerator in Storage.h; seed default 2026. (d) Why own code, not rand()? The spec says "own code, not rand()": it shows we understand how randomness is produced, and the output does not depend on a compiler's rand() implementation. Why a fixed seed? Reproducibility: every run, on every machine, gives the same 100 students, so demos, tests and the whole team's results match, and a bug can be reproduced. (e) O(students × achievements). Not suitable for security (an LCG is predictable), fine for fake data.

3.6 Tests – oracle testing

Files: tests/test_structures.cpp (yours), TestUtil.h (shared with Pranjal's pipeline tests).

Concept Q: oracle testing

(a) An oracle is a trusted source of the right answer. Here, the STL containers are the oracle: we do the same operations on our structure and on the STL one, then check the results match. Analogy: checking your maths answer with a calculator. (b) Example idea: push 10,000 numbers into DynArray<int> and a std::vector<int>; compare size and every element. Put/remove many random keys in HashMap<int,int> and in std::unordered_map, then compare size() and every find. (c) Only inside tests/; the program itself has no STL containers. (d) Why oracle testing, not hand-picked cases? Hand-picked cases miss odd situations (many collisions, rehash boundaries). Random comparison against a trusted structure covers more with less effort. (e) A test is only as good as its checks: it proves agreement on the inputs tried, not for all inputs.

What exactly each test file asserts is not detailed in the spec; describe it in your own words from your code.

4. Two worked traces

Trace 1: loading one CSV line into DataStore

Take this achievements line (example values): 12,7,CODING,Won Weekly Contest,05-03-2026,80,codeforces,link_to_proof,Approved

  1. loadFromCsv opens the file with std::ifstream. If it cannot open it, it returns false.
  2. It reads the header line and skips it, then loops with getline until the end of the file.
  3. For this line, splitLine(line, ',', parts) fills a DynArray<std::string> with 9 pieces: id, studentId, type, title, date, score, platform, proof, status.
  4. Numbers come as text, so id, studentId, score are converted to int (for example with std::atoi; <cstdlib> is on the allowed list; the exact conversion call is not in the spec).
  5. The loader calls the factory createAchievement("CODING", 12, 7, "Won Weekly Contest", "05-03-2026", 80, "link_to_proof", "codeforces"), which returns a CodingAchievement* (or nullptr if the type is unknown, in which case the row is skipped or reported).
  6. The status column ("Approved") is applied to the new object. The spec states a new object starts as Pending and only approve() / reject() change it, so the loader must go through those methods.
  7. addAchievement(a) runs: it checks the id with the HashMap (find). If the id is new: put(12, a) into achievements and achievementOrder.push_back(12), return true. If the id already exists, return false, and the store does not delete the object.
  8. For the students file, the same steps happen with 8 columns, and the skills column is split again on ';' with splitLine(skills, ';', skillParts), each piece being added to the student's HashSet<std::string> via addSkill.
  9. At the end the nextStudentId / nextAchievementId counters should be above the largest id seen, so new ids never clash (exact rule not detailed in the spec).

Trace 2: a put that triggers a rehash

Setup: a HashMap<int,int> with 16 buckets. Assume the int hash is the key itself (the spec does not say), so bucket = key mod 16. It currently holds 12 keys, so load factor = 12/16 = 0.75, which is not above 0.75. Keys 3 and 19 are both in bucket 3 (3 mod 16 = 3, 19 mod 16 = 3, a collision chain).

  1. put(35, 100) is called. 35 mod 16 = 3, so we walk bucket 3's chain: 3 (no), 19 (no), end. Key is new.
  2. Make a new node {35, 100, next} and link it into bucket 3's chain. size becomes 13.
  3. Check load factor: 13/16 = 0.8125 > 0.75, so rehash. (Whether the check runs just before or just after insertion is not stated in the spec; the result for the user is the same, a bigger table.)
  4. Allocate a new bucket array of 32 pointers, all nullptr.
  5. Walk each old bucket and each node in its chain. For each node compute the new bucket: key mod 32. Re-link the same node into the new table (no need to create a new node).
    • key 3: 3 mod 32 = 3 → new bucket 3
    • key 19: 19 mod 32 = 19 → new bucket 19 (the chain is split!)
    • key 35: 35 mod 32 = 3 → new bucket 3 (shares with key 3)
  6. delete[] the old bucket array (only the array of pointers; the nodes live on in the new table).
  7. Update bucket count to 32. Now load factor = 13/32 = 0.41, chains are shorter again.
Why is one rehash still amortised O(1)?It costs O(n), but it happens only when size reaches 0.75 × capacity, then capacity doubles, so the next rehash is about as far away as the current size again. Total rehash work for n inserts is about n + n/2 + n/4 + ... < 2n, so per insert it averages a constant.

5. Edge cases and honest limitations

SituationWhat happens / why it matters
All keys land in one bucketThe chain is the whole list: worst case O(n) for put/find/remove. Average stays O(1) only if the hash spreads keys well.
find on a missing keyReturns nullptr. Caller must check, or the program crashes.
Pointers returned by find after a rehashA rehash re-links nodes (the spec says every node is re-inserted). Do not keep an old pointer across a put; look it up again. Also, in DynArray, a pointer or reference from operator[] is invalid after push_back grows the array (the block moved).
Copying a HashMap / HashSet / DataStoreNot allowed (= delete), a compile error. Pass by reference.
Copying a DynArrayAllowed and deep, O(n). Copying a DynArray<Achievement*> copies the pointers, not the objects (non-owning).
operator[] with a bad indexSpec gives no bounds-check promise. Treat out-of-range as your mistake (undefined behaviour unless the code checks).
removeAt bad indexReturns bool; false means "index not valid, nothing removed" (this is what a bool return suggests; confirm with your code).

7. Viva questions and model answers

Say the answer in your own words. Keep it short; then give the example if asked.

1. What is your role in the project?
I built the foundation layer: DynArray, HashMap, HashSet, DataStore (owner of all objects plus CSV load/save), DataGenerator (100 reproducible students), and the structure tests.
2. Why did the project avoid STL containers?
It is a DSA project. We must show that we can build the structures ourselves. STL is used only in tests as an independent checker.
3. Why not just use arrays?
A plain array has a fixed size and a linear search for finding a student by id (O(n)). DynArray grows on demand, and for lookup by id we use a hash map (about O(1)). An array is still right when we need ordered, index-based access, and DynArray gives that.
4. How does DynArray grow?
When size equals capacity, it allocates a block of double the capacity (starting at 4), copies the items, frees the old block, then adds the new item.
5. Why double, not +1?
Growing by +1 copies everything on every push: 1+2+...+n is about n²/2, so O(n) per push. Doubling makes copies add up to under 2n total, so O(1) average.
6. What does "amortised O(1)" mean? Is any single push slow?
Average cost per operation over a long sequence. Yes: the push that triggers growth costs O(n). Those are rare, so the average is constant.
7. What is the Rule of Three?
If a class owns a resource, write the destructor, copy constructor and copy assignment together. For DynArray they free memory and deep-copy.
8. Deep copy vs shallow copy?
Shallow copies the pointer, so two objects share one block, and both free it later (double free). Deep makes a new block and copies the values.
9. Why is copy deleted for HashMap?
Copying would have to rebuild every node and is never needed; passing by reference is enough. Deleting it turns accidental copies into compile errors, and avoids the shallow-copy double free.
10. What does = delete do?
It forbids a function. If code tries to use it, compilation fails.
11. What is RAII?
A resource is acquired in the constructor and released in the destructor, so cleanup is automatic when the object goes out of scope. Our containers free their memory in their destructors.
12. Why templates?
One blueprint works for many types (DynArray<int>, HashMap<int,Student*>) without copy-pasting code, and there is no runtime cost.
13. How does a hash map work?
A hash function turns a key into a number; number mod bucket count gives the bucket; the bucket holds a chain of nodes; we walk the chain comparing keys. Average O(1).
14. What is stored in a bucket?
A pointer to the first node of a linked chain (or nullptr if empty). Each node holds key, value and a next pointer.
15. What if two keys collide?
Both nodes go into the same bucket's chain (separate chaining). To find one, we walk the chain and compare real keys. That is why the node stores the key.
16. Describe your string hash.
Polynomial rolling hash with base 31: h = h*31 + char for each character. Each position gets a different weight, so "ab" differs from "ba".
17. What is the load factor and when do you rehash?
Load factor is size divided by bucket count. When it goes above 0.75, we double the buckets and re-insert every node.
18. Why must you re-insert nodes after growing, rather than copy the buckets?
The bucket index is hash mod bucketCount. When bucketCount changes, the index changes, so each node must be re-placed.
19. Why is rehash still amortised O(1)?
A rehash is O(n) but happens only after the size grows by about double; the total over n inserts is about n + n/2 + n/4 + ... < 2n.
20. What is the worst case for HashMap?
O(n) for put/find/remove, if all keys land in one bucket (one long chain). It is rare with a good hash and rehashing.
21. Why chaining instead of open addressing?
It is simpler to write and delete from, and a full table is never an issue (chains just grow). Open addressing is more cache-friendly but needs tombstones for deletion.
22. Why hash map and not a BST / sorted array for student lookup?
We only need exact-key lookup, which a hash map does in about O(1). A BST gives O(log N) and its advantage (ordering) is not needed here. (Ordering IS needed for the leaderboard, so Pranjal uses an AVL tree there.)
23. Why does find return a pointer?
It can express "not found" with nullptr and also allows in-place modification with one lookup. A reference cannot be null; a default value is ambiguous.
24. What if find returns nullptr and you dereference it?
Undefined behaviour, usually a crash. Always check first.
25. What is forEach and why is F a template parameter?
It calls any callable (lambda, function, functor) for every entry. A template parameter accepts all of them without STL's std::function, and without exposing the table's internals.
26. How is HashSet built?
By composition: it holds a HashMap<T,bool>; the item is the key, the bool is a dummy. add returns false if the key already exists. All operations are average O(1).
27. Who owns the Student and Achievement objects? Who deletes them?
DataStore owns them; its destructor (and clear()) deletes them. Other classes only keep non-owning pointers. The base destructor is virtual so subclasses are destroyed correctly.
28. Why keep studentOrder and achievementOrder arrays when you already have hash maps?
A hash map has no stable order. The arrays record insertion order, so the saved CSV always has the same order.
29. How is the CSV parsed, and why are commas removed from text?
Each line is cut with splitLine at commas. Our splitter does not understand quotes, so a comma inside a title would shift columns. We strip commas from free text (and the CLI rejects them). Trade-off: simple code, but commas are lost.
30. Why a fixed seed and your own LCG for generated data?
A fixed seed (2026) gives identical data on every run, so demos, tests and debugging are reproducible. The LCG is our own code, not rand(), to show how pseudo-randomness works and avoid compiler differences. It is not secure.
31. How do you know your structures are correct?
Oracle testing: run the same operations on our structure and on an STL one (inside tests only) and compare results. It increases confidence but cannot prove correctness for all inputs.
32. What if addStudent is given an id that already exists?
It returns false and does not store it. The store does not delete the object, so the caller must, or it leaks.
33. Tricky: after a rehash, is a pointer you got from find still valid?
Do not rely on it. The nodes are re-linked in a new table, so refetch with find after any put. (Same for DynArray pointers after growth.)
34. Tricky: which part of the system depends on your code most?
Almost everything: DataStore's maps resolve every id lookup, reviewNext uses the registry HashMap, RankEngine's three HashMaps hold scores and daily counts, and Student's skills use HashSet.
