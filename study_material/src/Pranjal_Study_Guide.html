1. The project in one page

The problem

A college has many students who do many things: contests, internships, certificates, open-source work. Today there is no single place that scores all of this fairly and shows who is on top. GEHU Forge is a C++ program that stores students and their achievements, checks (verifies) each achievement, turns it into points, and keeps a live leaderboard (a list sorted by score, best first).

Why no STL containers?

The STL (Standard Template Library) gives ready-made containers like vector, map, set. This is a Data Structures project, so the evaluators want to see that we can build them. The rule in our spec: the program uses no STL containers. We may still use std::string, iostream, fstream, cmath, iomanip. The test files may use STL only as an independent "oracle" (a trusted answer to compare our own structures against).

Data and CLI

  • 100 synthetic students (fake, made by our own seeded generator, seed 2026) are stored in two CSV files: students.csv and achievements.csv. CSV means "comma-separated values", a plain text table.
  • The CLI (command-line interface, a text menu) lets the user add students and achievements, review pending ones, see the Top 10, look up one student's rank and profile card, and save.
Your one-line pitch: "I built the ranking core. Every time a verified achievement arrives, we turn it into points, update the student's EXP, and move them in a balanced tree in O(log N). Because every tree node stores its subtree size, we can also answer 'what is this student's rank?' in O(log N) instead of scanning everyone."

2. System architecture and flow

Read the picture top to bottom. Your parts are in yellow.

The flow in numbered steps (from the spec)

  1. Load: DataStore::loadFromCsv (Saksham) reads data/students.csv and data/achievements.csv. If the files are missing, DataGenerator makes 100 synthetic students (seed 2026). DataStore owns a HashMap<int,Student*> and a HashMap<int,Achievement*>.
  2. Submit: in the CLI "Submit achievement", App (Divyanshi) validates the input and builds the Achievement object. Its status starts as Pending.
  3. Queue: VerificationService::submit(a) (Manya) puts the achievement id into a LinkedQueue<int> (first in, first out).
  4. Review: CLI "Review next" calls VerificationService::reviewNext(registry, approve). Approved calls Achievement::approve(), otherwise reject() (a small state machine).
  5. Score (YOU): RankEngine::applyAchievement(student, ach) runs. It first calls ach.tryConsumeForScoring() (the "score only once" guard).
  6. Weighted points = base x categoryWeight x platformMultiplier x dailyDecay.
  7. The raw score goes through log normalisation to give EXP (0 to 10000).
  8. HashMap erase/update O(1) and AVLTree erase + insert O(log N).
  9. Query (YOU): the AVL leaderboard gives getTopK(10) in O(K + log N) and getRank(id) in O(log N).
  10. Show: the CLI prints the leaderboard or a profile card (Student::printProfileCard, Divyanshi).

3. Your modules, concept by concept

Note on code snippets: The snippets below are short teaching sketches of the idea, written to match the spec's names. The real files follow the spec; tiny details (like variable names) may differ. Always explain the idea, not the exact line.

3.1 Binary Search Tree (BST)

(a) Definition. A tree is a set of nodes joined by links. A binary tree gives each node at most two children: left and right. A binary search tree adds one rule: everything in a node's left subtree is "smaller" and everything in its right subtree is "bigger". (A subtree is a node plus everything below it.)

(b) How it works. To find a value, start at the root. If it is smaller, go left; if bigger, go right; stop when you find it or hit nothing. Each step throws away half the tree if the tree is well shaped. Analogy: guessing a number from 1 to 100 with "higher / lower" hints.

(c) Where. AVLTree is a BST. The only twist: our "smaller" means "better rank" (see 3.7), so the leftmost node is rank 1.

(d) Why not a plain array/list? Sorted array: insert is O(n) because you shift items. Linked list: search is O(n). A tree gives O(log N) for both when balanced.

(e) Complexity. Search/insert/delete: O(height). Height is about log2(N) if balanced, but N if not (next section).

3.2 Why a plain BST can become O(n)

The shape of a BST depends on the order in which you insert. If students arrive already sorted (10, 20, 30, 40, 50), each new value goes right of the last one. The tree becomes a stick (really a linked list). Then "go left or right" never skips anything and each operation walks all N nodes.

Plain BST after inserting 1,2,3,4,5 in order: height 5, search O(n)
Same keys, balanced: height 3, search O(log n)
Key sentence: A plain BST is only fast if we are lucky with the insert order. An AVL tree repairs itself so we are never unlucky. With N = 1,000,000 that is about 20-29 steps instead of 1,000,000.

3.3 AVL tree: height and balance factor

(a) Definition. An AVL tree (named after Adelson-Velsky and Landis) is a BST that keeps itself balanced. Two small terms first:

  • Height of a node = the number of nodes on the longest path from it down to a leaf. A missing child (null) has height 0, a leaf has height 1. (Some books count a leaf as 0. Either is fine if you stay consistent. Say which one you use.)
  • Balance factor (BF) of a node = height(left) - height(right).

AVL rule: every node must have BF in {-1, 0, +1}. If an insert or delete makes a BF become +2 or -2, we fix it with a rotation.

(b) How it works. Insert like a normal BST (recursively). On the way back up, for every node: (1) recompute its height and size, (2) compute BF, (3) if |BF| = 2, rotate. Because only the nodes on one root-to-leaf path can change, this costs O(log N).

(c) Where. AVLTree::insert and AVLTree::erase. isBalanced() checks that every node obeys the rule, so tests can prove it.

(d) Why guaranteed? The AVL rule forces the tree to be bushy: height is at most about 1.44 x log2(N+2). So the height is always O(log N).

(e) Complexity. insert, erase, rankOf: O(log N). Space: O(N) nodes.

int heightOf(const Node* n) { return n ? n->height : 0; }
int sizeOf(const Node* n) { return n ? n->size   : 0; }
int balanceOf(Node* n) { return heightOf(n->left) - heightOf(n->right); }
void update(Node* n) {                 // call after any change below n
    n->height = 1 + max(heightOf(n->left), heightOf(n->right));
    n->size   = 1 + sizeOf(n->left) + sizeOf(n->right);
}

3.4 The four rotation cases: LL, RR, LR, RL

Definition. A rotation is a small local re-wiring of 2-3 pointers that changes the shape of the tree (making it flatter) while keeping the BST order correct. Think of a rope hanging over a pulley: you swap which element is on top without changing the left-to-right order.

LL case (left-left): fix with one right rotation

Insert 30, 20, 10. Each goes left of the last, so the tree leans left. The BF of 30 is +2.

Before: 30 -> 20 -> 10 leans left. Balance factor of 30 is +2
After rotateRight(30): 20 is the new root

RR case (right-right): fix with one left rotation

Insert 10, 20, 30. This is the picture to draw on the whiteboard first. BF of 10 is -2. Rotate left around 10: its right child 20 moves up, 10 becomes 20's left child.

Before: 10 -> 20 -> 30 leans right. Balance factor of 10 is -2
After rotateLeft(10): 20 is the new root
Node* rotateLeft(Node* x) {      // x = unbalanced node, y = its right child
    Node* y = x->right;
    x->right = y->left;          // y's left subtree becomes x's right
    y->left  = x;                // x goes below y
    update(x);                   // x is lower now, so update it FIRST
    update(y);
    return y;                    // y is the new top of this subtree
}
// rotateRight is the exact mirror image (swap left and right).

LR case (left-right): two rotations

Insert 30, 10, 20. The node 30 is left-heavy, but its left child 10 is right-heavy, so one rotation is not enough (it would only move the problem). First rotate the child left, which turns the shape into LL; then rotate right.

Before (insert 30,10,20): zig-zag. 30 is left-heavy but its left child 10 is right-heavy
Step 1: rotateLeft(10) turns it into the LL shape
Step 2: rotateRight(30). Balanced

RL case (right-left): mirror of LR

Before (insert 10,30,20): zig-zag the other way
Step 1: rotateRight(30) turns it into the RR shape
Step 2: rotateLeft(10). Balanced

(c) Where / (d) Why / (e) Complexity: Rotations live inside AVLTree as rotateLeft and rotateRight; the four cases are decided after every insert and erase. We chose AVL (not Red-Black) because AVL balances more strictly (shorter tree, faster lookups) and its rules are much easier to explain on a whiteboard. A rotation is O(1): only a few pointers change.

Why the BST order stays correct: in the examples above, 10 < 20 < 30 reads the same left-to-right before and after. A rotation changes who is on top, never the in-order sequence.

3.5 Augmenting nodes with subtree size: rank in O(log N)

(a) Definition. To augment a data structure means adding extra information to each part so it can answer more questions. Our node is Node = {RankKey key; int height; int size; Node* left, *right;}. size is the number of nodes in that node's subtree (including itself). A rank is a student's position: rank 1 = best.

(b) How it works. Size is easy to keep right: size = 1 + size(left) + size(right). We recompute it in the same update step as height, on the way back up after insert, erase and every rotation. After the rotation example the tree looks like this (red = height h and size s):

To get a rank, walk down from the root with a running total acc (how many students are known to be before us). At each node:

  • If our key equals the node's key: rank = acc + size(left) + 1. (Everyone in the left subtree is before us, plus the node itself.)
  • If our key comes before the node: go left (nothing added).
  • Else: the node and its whole left subtree are before us, so acc += size(left) + 1; go right.
  • If we fall off the tree (null), the key is not there: return -1.
int rankOf(const RankKey& k) const {
    int acc = 0;
    Node* cur = root;
    while (cur) {
        if (same(k, cur->key))   return acc + sizeOf(cur->left) + 1;
        if (before(k, cur->key)) cur = cur->left;
        else { acc += sizeOf(cur->left) + 1; cur = cur->right; }
    }
    return -1;                       // not in the tree
}

(c) Where. AVLTree::rankOf, which RankEngine::getRank calls. (d) Why: our old version used std::set and found rank by walking the set from the top and counting: O(N). With sizes, we only walk one path: O(log N). For N = 1,000,000 that is about 20 steps instead of up to a million. (e) O(log N) time, O(1) extra space. Cost: one extra int per node and one extra line in update.

3.6 In-order traversal and top-K

(a) Definition. In-order traversal visits left subtree, then the node, then right subtree. On a BST this visits keys in sorted order. Because our before() puts the best student "first", in-order gives rank 1, 2, 3, ... Top-K means "the best K students".

(b) How it works. Walk in-order but stop as soon as K keys are collected (recursion returns early). We go down the left spine first (about log N steps), then collect K nodes. Example: on the 7-node tree in section 4.3, top 3 = id7 (9100), id3 (8200), id9 (7500).

void collect(Node* n, int k, DynArray<RankKey>& out) const {
    if (!n || out.size() >= k) return;       // stop early
    collect(n->left, k, out);
    if (out.size() < k) out.push_back(n->key);
    collect(n->right, k, out);
}

(c) Where. AVLTree::topK(int k, DynArray<RankKey>& out) and RankEngine::getTopK. The CLI "Top 10" uses it. (d) Why not sort everything? Sorting N students each time costs O(N log N). The tree is already sorted. (e) O(K + log N). For K=10: N=100 gives about 7+10 steps, N=1,000,000 gives about 20+10 steps. Almost the same!

3.7 Custom ordering before(a,b), tie-break, and the double problem

(a) Definition. The key is struct RankKey { double exp; int studentId; }. A tree needs a rule that says which of two keys goes first. Ours:

before(a, b) = a.exp > b.exp  ||  (a.exp == b.exp && a.studentId < b.studentId)
  • Higher EXP goes first (so the leftmost node is rank 1).
  • If EXP is exactly equal, the smaller studentId goes first. This is the tie-break.

Why a tie-break is needed. A tree wants a strict ordering: for any two different keys, exactly one is before the other. Two students with equal EXP would otherwise look "the same", and the tree could not tell them apart when erasing. Adding studentId (unique per student) makes every key unique, so ranks are never ambiguous and results are the same every run.

Where / Why / Complexity. Used in insert, erase, rankOf. Each comparison is O(1).

The double problem. EXP is a double (a decimal number stored in binary). Doubles cannot store every decimal exactly, and the same maths done in two different ways can differ in the last digit. Comparing with == is therefore risky. Our rule: we never recompute the old EXP to find the old key. We save the exact value in expMap when we insert it, and when the EXP changes we read that exact stored value back and erase with it. The bits are identical, so == matches. If we instead recomputed it, the erase might silently fail and leave a ghost node, giving the student two entries.

3.8 Recursion, pointers, destructor and Rule of Three

Pointer: a variable that holds the memory address of another object (Node*). Heap: memory we get with new and must give back with delete. Recursion: a function that calls itself on a smaller problem; here, on the left or right subtree. The base case is if (!n) return ....

How it connects. Every node is made with new Node. A tree of N nodes means N separate heap blocks. If nobody frees them, we get a memory leak (memory taken and never returned). So ~AVLTree() calls a recursive destroy(Node*) that frees the children first, then the node (post-order):

void destroy(Node* n) {
    if (!n) return;
    destroy(n->left);
    destroy(n->right);
    delete n;
}
~AVLTree() { destroy(root); }
AVLTree(const AVLTree&) = delete;            // copying is forbidden
AVLTree& operator=(const AVLTree&) = delete;

Rule of Three. If a class needs a custom destructor, it almost certainly also needs a custom copy constructor and copy assignment. Why? The default copy only copies the pointer (a "shallow copy"), so two trees would point to the same nodes, and both destructors would free them: a double free crash. Two ways to be safe: write a deep copy (as DynArray does) or delete the copy operations (as AVLTree, HashMap and LinkedQueue do). We chose delete for the tree because nobody needs to copy a leaderboard, and a deep copy is extra code that could hide bugs.

Complexity. Destroying costs O(N); recursion depth is the tree height, only O(log N), so there is no stack-overflow risk even for a million nodes (a stick-shaped plain BST could overflow!).

3.9 The hybrid design: HashMap + AVLTree

(a) Definition. A hash map stores key-value pairs and finds a key in average O(1) by turning the key into a bucket number (a hash). Our HashMap (Saksham) uses separate chaining: each bucket holds a linked list. Hybrid here means: use two structures together, each for what it does best.

(b) The problem both solve. When a student earns a new achievement, their position changes. To move them in the tree we must erase the old key (oldEXP, id). But the tree is sorted by EXP, so you cannot find a node by id alone. We need to know the old EXP first.

  1. expMap (HashMap): look up the old EXP by studentId. Average O(1).
  2. board.erase({oldExp, id}): O(log N).
  3. Compute the new EXP and expMap.put(id, newExp): O(1).
  4. board.insert({newExp, id}): O(log N).

(d) Why both? HashMap alone: fast "what is EXP of id 42?" but no ordering, so top-10 needs sorting everything, O(N log N). Tree alone: ordered, but to find "id 42's old EXP" you would scan every node, O(N). Together: every operation is O(log N) or better.

(c) Where. RankEngine members: HashMap<int,double> rawScore, HashMap<int,double> expMap, HashMap<std::string,int> dailyCount, AVLTree board. (e) One re-rank = O(1) + O(log N) + O(log N) = O(log N).

3.10 RankEngine maths

The EXP is the student's final score, from 0 to 10,000. The pipeline is: weighted points, then daily decay, then add to raw score, then normalise to EXP, then pick a tier.

Where these numbers live: In the spec, the weights and multipliers are virtual functions of the Achievement classes (Manya): categoryWeight() and platformMultiplier(). The non-virtual weightedPoints() combines them. RankEngine just calls a.weightedPoints(). This is polymorphism: the engine does not need a switch on type; each class knows its own weight. (Our old RankEngine had the switch inside itself.)

Negative-score cushion 0.3

A score can be negative (e.g. a rating drop in a contest). weightedPoints() then returns basePoints x 0.3 instead of multiplying by weights. So a drop of -100 only costs -30 raw points: a fall hurts, but not as much as a gain helps. Also raw = max(0, raw + delta), so raw never goes below zero.

Daily activity decay (anti-spam)

Without it, someone could submit 50 tiny achievements in one day to climb. The engine counts how many achievements a student has had on the same date, using HashMap<std::string,int> dailyCount with the key "studentId|date" (for example "7|12-03-2026"). RankEngine does this itself.

Count that dayDecay
1st to 5th1.0 (full points)
6th to 10th0.4
11th and more0.1

Decay applies only to positive deltas; a penalty is never "decayed" (so you cannot dodge it).

Logarithmic normalisation

EXP = min(10000, 10000 * ln(1 + raw) / ln(1 + 50000))

Here ln is the natural logarithm. The log is a function that grows quickly at first, then slows down. ln(1 + 50000) = 10.8198, so raw = 50000 gives exactly 10000, and anything above is capped at 10000.

3.11 OOP design: single responsibility and composition

  • Single Responsibility Principle: a class should have one job. RankEngine's job: score and rank. It does not decide whether an achievement is genuine; that is VerificationService (Manya). It does not load files (DataStore) or print menus (App).
  • The contract between them: RankEngine relies on Achievement::tryConsumeForScoring(). That method returns true only if the status is Approved and points were not applied before, and it sets pointsApplied = true in the same call (an atomic check-and-set). So an achievement can never be counted twice, even if the engine is called twice by mistake.
  • Composition (HAS-A): RankEngine contains an AVLTree and three HashMaps as members. It is not derived from them. Rule of thumb: use inheritance for "is-a" (a Student IS-A User), composition for "has-a". Benefit: the engine can be changed without exposing the tree to the outside.
  • Encapsulation: outside code only sees getTopK, getRank, getExp, rankedCount, tierBadge. It cannot touch the tree and break the balance.

4. Worked traces

4.1 applyAchievement step by step

Student id 7 (new, no EXP yet). Achievement: Coding, platform Codeforces, score 1200, date 12-03-2026, status Approved (Manya's reviewNext just approved it).

  1. Guard: a.tryConsumeForScoring(). Status is Approved and pointsApplied is false, so it returns true and sets pointsApplied = true. (If it had returned false, applyAchievement returns false and nothing changes.)
  2. Daily count: key = "7|12-03-2026". ++dailyCount[key] gives 1. Count is 5 or less, so decay = 1.0.
  3. Weighted points: weightedPoints() = base x categoryWeight x platformMultiplier = 1200 x 3.5 x 2.5 = 10,500. The score is positive, so delta = 10,500 x 1.0 = 10,500.
  4. Raw score: student 7 had no raw score (treated as 0). raw = max(0, 0 + 10500) = 10,500. Save it in rawScore.
  5. Normalise: EXP = 10000 x ln(10501) / ln(50001) = 10000 x 9.2592 / 10.8198 = 8557.67 (below the 10000 cap, so no capping).
  6. Re-rank: student 7 is not in expMap, so there is no old key to erase. expMap.put(7, 8557.67) and board.insert({8557.67, 7}).
  7. Tier: 8557.67 is at least 7000 but less than 9000, so Master.

Second achievement, same day. Open-source, score 200. Count for "7|12-03-2026" becomes 2, so decay 1.0. Weighted = 200 x 2.5 x 1.0 = 500. raw = 10,500 + 500 = 11,000. EXP = 10000 x ln(11001)/10.8198 = 10000 x 9.3057/10.8198 = 8600.66. Now the old EXP (8557.67) is in expMap, so we use it to erase the old key (see 4.2).

A spam example. If this was the 6th achievement of that day with a weighted value of 500, the decay is 0.4, so delta = 200 and raw grows only by 200. The 11th would add 50.

4.2 Re-ranking when EXP changes

Same student 7 after the second achievement. Steps (all inside applyAchievement):

  1. double* old = expMap.find(7) gives a pointer to 8557.67 (not null, so the student is already ranked).
  2. board.erase({*old, 7}) uses the exact stored value. The tree searches with before(), finds the node, removes it, then rebalances and updates sizes on the way up. O(log N).
  3. expMap.put(7, 8600.66).
  4. board.insert({8600.66, 7}). O(log N). The student may now be higher: for example from rank 5 to rank 4.
// the heart of the re-rank (sketch)
double newExp = normalize(raw);
if (double* old = expMap.find(id))
    board.erase(RankKey{*old, id});     // exact old value from expMap
expMap.put(id, newExp);
board.insert(RankKey{newExp, id});
Why order matters: If we put the new EXP into expMap before erasing, we would lose the old value and could not erase the old node. Always: read old, erase old, store new, insert new.

4.3 getRank on a 7-node tree using sizes

Seven students. Each node shows id and in red EXP and s = subtree size. Remember: left = better (higher EXP).

In-order (left, node, right) gives ranks: id7 (9100), id3 (8200), id9 (7500), id1 (6000), id4 (5200), id8 (3100), id2 (900), i.e. ranks 1 to 7.

8. Viva: 32 questions with model answers

Answer in your own words. The model answer is the shortest correct version; add one example if you have time.

Q1. What is a binary search tree?
A tree where each node has at most two children, and everything on the left is smaller and everything on the right is bigger than the node. It lets us search by discarding half the tree at each step.
Q2. Why AVL and not a plain BST?
A plain BST can become a stick if keys arrive in order, giving O(n) operations. An AVL tree rebalances with rotations so the height is always O(log N), so every operation is O(log N) even in the worst case.
Q3. What is a balance factor?
Height of the left subtree minus height of the right subtree. AVL requires it to be -1, 0 or +1 at every node. At +2 or -2 we rotate.
Q4. What are the four rotation cases?
LL (fix with one right rotation), RR (one left rotation), LR (left rotation on the left child, then right rotation), RL (right rotation on the right child, then left rotation).
Q5. Why is LR not fixed by one rotation?
Because the heavy part is in the middle (left child's right side). A single right rotation just moves the heaviness to the other side. We first straighten it into LL with a left rotation on the child.
Q6. Does a rotation break the sorted order?
No. The in-order sequence is the same before and after; only the shape changes. A rotation changes 2-3 pointers, so it is O(1).
Q7. Why store size in every node?
So we can compute rank in O(log N). The size of the left subtree tells how many students are ahead without visiting them. It costs one int per node and one line in the update step.
Q8. How do you compute a rank from sizes?
Walk down from the root with a running count. Going right past a node adds size(left)+1. When we reach the key, rank = count + size(left) + 1. If we fall off the tree, return -1.
Q9. How was rank done in the old version, and how is it now?
Old: a linear scan over std::set, O(N). Now: rankOf with subtree sizes, O(log N).
Q10. Why do you need both a hash map and a tree?
The tree is sorted by EXP, so you cannot find a student's node by id alone. The hash map gives the student's old EXP in O(1), then the tree erases and re-inserts in O(log N). The map alone cannot rank; the tree alone cannot look up by id.
Q11. What if two students have identical EXP?
The ordering breaks the tie by studentId: smaller id ranks first. This makes the ordering strict, so every key is unique and the results are the same every time.
Q12. What is a strict ordering and why does the tree need one?
For any two different keys, exactly one is before the other. Without it, equal-looking keys cannot be told apart for erase or rank.
Q13. Why do doubles need care?
They cannot store every decimal exactly, and equal-looking results can differ in the last bit. So we never recompute the old EXP: we read the exact stored value from expMap and erase with that.
Q14. What is the complexity of top-10 for N=100 and N=1,000,000?
O(K + log N). For N=100: about 7 steps to the left end plus 10 nodes. For N=1,000,000: about 20 steps plus 10. The log N part grows very slowly, so both are fast.
Q15. What is the complexity of applyAchievement?
O(log N): an average-O(1) hash lookup and update, plus one erase and one insert on the tree, each O(log N).
Q16. Why log scaling for EXP?
It rewards early progress (the first points give a lot of EXP), stops one huge score from dominating, and keeps EXP bounded between 0 and 10,000 so tiers are simple.
Q17. Compute EXP for raw = 10,500.
10000 x ln(10501) / ln(50001) = 10000 x 9.2592 / 10.8198, about 8558. That is the Master tier.
Q18. How do you get raw = 10,500 for a 1200 Codeforces CP achievement?
1200 x category weight 3.5 x platform multiplier 2.5 = 10,500, with decay 1.0 because it is among the first five that day.
Q19. Why can't a heap give rank?
A heap only keeps the maximum at the top and is only loosely ordered below it. It has no way to count how many items are ahead of a given student, and no efficient delete of an arbitrary item. Top-K needs K pops that destroy it.
Q20. Why not std::set?
STL containers are not allowed in this project, and std::set has no rank query (it would be an O(N) walk). Our tree is augmented with sizes.
Q21. AVL vs Red-Black: why AVL?
AVL is stricter about balance, so the tree is shorter and queries are faster, and it has only four simple cases. Red-Black does fewer rotations on updates. For a ranking board with many rank queries and easy teaching, AVL fits.
Q22. Why Rule of Three here?
AVLTree owns heap nodes and frees them in its destructor. A default copy would copy only the root pointer, so two trees would free the same nodes (double free). So we also handle copying: we delete the copy constructor and copy assignment.
Q23. How does the destructor free the tree?
It calls a recursive helper that frees the left child, the right child and then the node (post-order). Recursion depth equals the tree height, which is O(log N), so it is safe.
Q24. What is the daily decay and why have it?
Anti-spam. For one student on one date: achievements 1-5 count x1.0, 6-10 x0.4, 11+ x0.1. It stops someone farming points with many small submissions in a day.
Q25. How does RankEngine count achievements per day?
With its own HashMap<std::string,int> keyed by "studentId|date". It increments the counter each time an achievement is applied.
Q26. What is the negative-score cushion?
Negative scores are multiplied by 0.3, and raw is clamped at 0. A bad contest costs a little, not a lot.
Q27. What is the single responsibility of RankEngine?
Scoring and ranking only. Verification belongs to VerificationService. RankEngine trusts Achievement::tryConsumeForScoring() to say whether an achievement may count.
Q28. What does tryConsumeForScoring do and why is it needed?
It returns true only if the achievement is Approved and not yet applied, and it marks it applied in the same call. This prevents counting an achievement twice.
Q29. What is composition and where do you use it?
A class HAS-A member of another class. RankEngine has an AVLTree and HashMaps as members (not inheritance). Also HashSet is built on HashMap, and Student has a HashSet.
Q30. What happens when you ask for the rank of an unranked student?
RankEngine::getRank returns -1. The caller must check for it.
Q31. Who owns the Student and Achievement objects?
DataStore. Its destructor deletes them. Student, VerificationService and RankEngine only keep non-owning pointers or ids.
Q32. What are the limitations of your design?
Synthetic data only; weights chosen by us, not validated; decay depends on date text being consistently formatted; single user, in memory; hash maps are only average O(1). We have not benchmarked at large scale.
