1. The project in one page

What problem does GEHU Forge solve?

Students at a college do many things: coding contests, certificates, open-source work, internships. Today these live in different places and nobody can compare them fairly. GEHU Forge is a talent and ranking platform. Students submit achievements. A reviewer checks them. Approved achievements turn into points (called EXP, from 0 to 10000), and students appear on a ranked leaderboard.

Why "no STL"?

STL (Standard Template Library) gives ready-made containers like vector, map and queue. This project is about Data Structures and Algorithms, so the team builds its own containers. If we used std::queue, we would show nothing about how a queue works. The rule: no vector, map, set, queue, unordered_*, list, stack, deque, pair, unique_ptr. Allowed: std::string, <iostream>, <fstream>, <cmath>, <iomanip>, <cstdlib>. (Test files may use STL only as an independent "oracle" to cross-check our own structures.)

Data and interface

  • 100 synthetic (made-up) students are generated with a fixed seed (2026) and stored in CSV files: data/students.csv and data/achievements.csv. If the files are missing, a generator creates them. CSV means "comma-separated values": a plain text table.
  • A CLI (command-line menu) lets you add students, submit achievements, review the next pending one, and show the Top 10 leaderboard. Menu: 1 Top 10, 2 Top K, 3 Student profile, 4 Add student, 5 Submit achievement, 6 Review next pending, 7 Rank of a student, 8 Dataset statistics, 9 Save, 10 Reset to synthetic seed, 0 Save and exit. There is also a scripted --demo mode.
  • Build: g++ -std=c++17 -Wall -Wextra main.cpp -o forge.exe
Your one-sentence pitch (Manya) "I built the part that decides what an achievement is and whether it is allowed to count: an abstract Achievement class with four types, a hand-made FIFO queue for the review line, and a VerificationService that approves or rejects in order. I make sure only approved achievements can be scored, and only once."

2. System architecture and flow

The picture below shows the journey of one achievement. Orange boxes are Manya's parts. Blue boxes belong to teammates.

The flow, step by step

  1. On start, DataStore::load (Saksham) reads the two CSV files (or lets DataGenerator create data if the files are missing).
  2. DataStore owns a HashMap<int,Student*> and a HashMap<int,Achievement*>.
  3. The CLI option "Submit achievement" (Divyanshi) validates the input and builds an Achievement object. Its status is Pending. (Manya)
  4. VerificationService::submit(a) puts the achievement id into a LinkedQueue<int>, which is first-in-first-out. (Manya)
  5. The CLI option "Review next" calls VerificationService::reviewNext(registry, approve). (Manya)
  6. If approved, Achievement::approve() runs, otherwise reject(). This is the state machine. (Manya)
  7. RankEngine::applyAchievement(student, ach) (Pranjal) is then called. It first calls ach.tryConsumeForScoring(), the score-once guard.
  8. Weighted points = base × categoryWeight × platformMultiplier × dailyDecay. The raw score goes through log normalisation to give EXP (0..10000).
  9. HashMap erase/update is O(1); AVLTree erase + insert is O(log N).
  10. The AVLTree leaderboard answers getTopK(10) in O(K + log N) and getRank(id) in O(log N).
  11. The CLI prints the leaderboard or the profile card (Student::printProfileCard, Divyanshi).

4. Concepts, one by one

Every concept has five parts: (a) plain definition, (b) how it works with a picture or tiny example, (c) where it is in the project, (d) why this and not the alternative, (e) complexity if it applies. The code snippets are short teaching sketches that use the spec's names. Your real files are the final truth.

Part A: Achievement.h (OOP)

A1Class and object

(a) A class is a blueprint (like a form template). An object is one filled-in copy (one student's actual form). A class bundles data (members) with functions (methods) that work on that data.

(b) The class says "every achievement has an id, a title, a score, a status". One object says "achievement 17: 'Codeforces Round Winner', score 40, Pending".

(c) Achievement and its four derived classes in Achievement.h. Each row of achievements.csv becomes one object.

(d) Without a class, we would carry 9 loose variables for each achievement and could easily mix them up.

A2Encapsulation and access specifiers

(a) Encapsulation = keep data and the functions that change it together, and control who can touch the data. Access specifiers: public (anyone), protected (this class and its children), private (only this class).

(b) The state fields (status, pointsApplied, score ...) are protected. Outside code cannot write a.status = Approved. It must call a.approve(), which checks the rules first. Reading is allowed through getters like getStatus().

// outside code
a.status = VerificationStatus::Approved;   // ERROR: protected
a.approve();                               // OK: the method checks "am I Pending?"
bool ok = a.isApproved();                  // OK: read-only getter

(c) Achievement members id ... category; mutators approve(), reject(), tryConsumeForScoring(); getters getId ... getCategory.

(d) Why not make everything public? Then any teammate could set status = Approved on a Rejected item, or set pointsApplied = false and give the student EXP twice. Controlled mutators make the bad states impossible. Why protected and not private? The spec lets derived classes read the members directly (for example when computing their own display()).

Honest note: protected is slightly weaker than private, because a derived class could modify the fields. That is an accepted trade-off here.

A3Constructors and member-initializer lists

(a) A constructor runs automatically when an object is created and sets it up. It has the class name and no return type. A member-initializer list is the part after the colon that sets members before the constructor body runs.

Achievement(int id, int studentId, const std::string& title, const std::string& date,
            int score, const std::string& proof, AchievementCategory cat)
  : id(id), studentId(studentId), title(title), date(date), score(score), proof(proof),
    status(VerificationStatus::Pending), pointsApplied(false), category(cat) {}

(b) Every new achievement is forced to start as Pending with pointsApplied = false. Nobody can create an already-Approved one by accident.

(c) The base constructor in Achievement; each derived constructor (e.g. CodingAchievement(id, studentId, title, date, score, proof, platform)) passes the common values up to the base constructor with its own initializer list.

(d) Why the list and not assignment in the body? The list builds each member directly with its value (efficient for strings), and it is the only way to initialise const members, references, and base classes. Members are initialised in the order they are declared, not the order written in the list (a classic trap).

A4Inheritance (is-a)

(a) A derived class gets everything of a base class and can add or change things. Use it when the sentence "X is a Y" is true. "A CodingAchievement is an Achievement."

(b) Common data (id, title, status) is written once in Achievement. CodingAchievement adds only a platform string and its own weight/multiplier.

class CodingAchievement : public Achievement { ... };   // public inheritance = is-a

(c) The four derived classes in Achievement.h: weights 3.5 (Coding), 1.0 (Certificate), 2.5 (OpenSource), 5.0 (Internship).

(d) Alternative: one big class with a type field and many if/switch blocks. Adding a fifth type would mean editing many places. With inheritance you add one class and nothing else changes. Alternative 2: composition (has-a) fits "a Student has achievements", not "a coding achievement is an achievement".

A5Abstract class and pure virtual functions

(a) A virtual function can be replaced by a derived class. A pure virtual function is declared with = 0 and has no body in the base: "every child must provide this". A class with at least one pure virtual function is abstract: you cannot create an object of it.

(b)

virtual void        display() const = 0;
virtual double      categoryWeight() const = 0;
virtual std::string typeName() const = 0;

Achievement a(...);            // ERROR: Achievement is abstract
CodingAchievement c(...);      // OK: it overrides all three

(c) Achievement declares display, categoryWeight, typeName as pure virtual. Each of the four children implements all three.

(d) Why pure virtual? A plain "Achievement" has no meaning: what is its weight, how does it print? There is no sensible default. Making it pure virtual (1) stops anyone from creating a meaningless generic achievement, and (2) forces every new type to define weight and display, or it will not compile. If we gave a fake default weight like 0, a forgotten override would silently give wrong EXP.

A6Runtime polymorphism and virtual dispatch; override

(a) Polymorphism = "many forms": one call, different behaviour depending on the real object. Runtime (dynamic) polymorphism decides at run time using a hidden table of function addresses (the vtable). That lookup is called virtual dispatch.

(b) A base pointer can hold the address of any derived object. Calling a virtual function runs the derived version.

Achievement* p = new CodingAchievement(1, 7, "CF Div2 Win", "10-03-2026", 40, "link", "codeforces");
p->display();          // runs CodingAchievement::display()
p->categoryWeight();   // returns 3.5, not some base value
delete p;              // needs a virtual destructor (see A7)

(c) The DataStore holds Achievement* in HashMap<int,Achievement*>; VerificationService, RankEngine::applyAchievement(Student&, Achievement&) and the CLI use the base type and never need to know whether it is Coding or Certificate.

(d) Alternative: switch(type) everywhere. That spreads type knowledge across the whole program. With virtual dispatch, RankEngine does not change when a new type is added.

(e) Cost: one extra pointer lookup per virtual call, O(1). Each object carries one hidden vptr.

override: a keyword written after a derived method's signature, e.g. double categoryWeight() const override { return 3.5; }. It tells the compiler "this must replace a base virtual function". If you misspell the name or forget const, the compiler gives an error instead of quietly creating a new unrelated function.

A7Virtual destructor

(a) A destructor (~Name()) runs when an object dies and cleans up. A virtual destructor makes delete through a base pointer call the derived destructor first, then the base one.

(b) Achievement* p = new CodingAchievement(...); delete p;

  • With virtual ~Achievement(): ~CodingAchievement runs, then ~Achievement. Everything is cleaned.
  • Without it: only ~Achievement runs. The derived part (for example the platform string) is never destroyed properly. The C++ standard calls this undefined behaviour: leaks, crashes, or nothing visible, so it can hide until the demo.

(c) virtual ~Achievement() in Achievement.h. It matters because DataStore owns every Achievement* and its destructor deletes them, always through the base pointer.

(d) Rule: if a class has any virtual function and is used through a base pointer, give it a virtual destructor. Cost: one more vtable slot. The only "alternative" is a non-polymorphic design, which we do not have.

A8Virtual function with default behaviour; template-method idea

(a) A virtual function with a body in the base is optional to override: children may use the default or change it.

(b) platformMultiplier() returns 1.0 by default. basePoints() returns score by default. Only CodingAchievement overrides platformMultiplier(): codeforces 2.5, codechef 1.8, leetcode 1.2, hackerrank 0.8, any other platform 1.0.

double Achievement::platformMultiplier() const { return 1.0; }   // default
double Achievement::basePoints() const         { return score; } // default

// the "template method": fixed recipe, customisable steps
double Achievement::weightedPoints() const {      // NOT virtual
    double b = basePoints();
    if (b < 0) return b * 0.3;                    // cushioned penalty
    return b * categoryWeight() * platformMultiplier();
}

(c) Achievement::platformMultiplier, basePoints, weightedPoints; override in CodingAchievement.

(d) The template method pattern: the base class fixes the recipe (weightedPoints) and children only fill in the steps (basePoints, categoryWeight, platformMultiplier). The recipe is deliberately non-virtual so no child can break the rule. (Careful: this is the "template method" design pattern, not C++ templates; they are different things.) Why defaults? Only one type needs a multiplier. Forcing three classes to write return 1.0; is noise.

Example: a Codeforces achievement with score 40: 40 × 3.5 × 2.5 = 350 weighted points. A Certificate with score 40: 40 × 1.0 × 1.0 = 40. A negative score of −10 gives −10 × 0.3 = −3 (penalties are softened). (The daily decay is applied later, by Pranjal's RankEngine, not here.)

A9enum class (strongly typed enumeration)

(a) An enum is a named list of constants. An enum class keeps the names inside their own scope and does not silently convert to int.

(b)

enum class VerificationStatus { Pending, Approved, Rejected };
VerificationStatus s = VerificationStatus::Pending;   // must write the scope
int x = s;                                            // ERROR: no silent int conversion
// old style enum: names leak out, "Pending" could clash with another enum

(c) AchievementCategory { INTERNSHIP, COMPETITIVE_PROGRAMMING, OPEN_SOURCE, CERTIFICATION, GENERAL } and VerificationStatus { Pending, Approved, Rejected }. Helper: static const char* statusName(VerificationStatus) turns the status into printable text.

(d) Why not int status (0,1,2)? Magic numbers are unreadable and any int would be accepted (what is status 7?). Why not plain enum? Name clashes and accidental int mixing.

A10State machine and allowed transitions

(a) A state machine lists the possible states and which moves between them are allowed.

(b)

Current stateapprove()reject()
Pendingbecomes Approved, returns truebecomes Rejected, returns true
Approvedreturns false, no changereturns false, no change

bool Achievement::approve() {
    if (status != VerificationStatus::Pending) return false;   // guard
    status = VerificationStatus::Approved;
    return true;
}   // reject() is the same with Rejected

(c) Achievement::approve() and reject(). Only a Pending achievement can change.

(d) Without the guard, a Rejected achievement could later be flipped to Approved (a loophole), or an Approved one could be rejected after the student already got EXP (the leaderboard would then be wrong). Returning bool lets the caller know whether the change really happened. (e) O(1).

A11Idempotency and the check-and-set guard tryConsumeForScoring()

(a) An operation is idempotent if doing it twice has the same effect as doing it once (pressing a lift button twice still calls one lift). Check-and-set means testing a condition and changing the flag in one step, inside one function.

(b)

bool Achievement::tryConsumeForScoring() {
    if (status == VerificationStatus::Approved && !pointsApplied) {
        pointsApplied = true;      // "consume" the ticket
        return true;               // caller may add the points NOW
    }
    return false;                  // not approved, or already used
}

Think of it like a one-time coupon: the first valid use stamps it as used. Every later use is refused.

(c) Achievement::tryConsumeForScoring(). Pranjal's RankEngine::applyAchievement calls it first; if it returns false, no EXP is added.

(d) Why check-and-set in one function? If RankEngine did if(!a.isPointsApplied()) { add(); a.setApplied(); }, a programmer could forget the second line, or an error between them would let points be added twice. Putting both steps inside the achievement means the object protects itself. (Honest note: this program is single-threaded, so "atomic" here means "cannot be separated by the caller", not thread-safe locking.) Double-EXP situations it prevents: reviewing the same id twice, loading an already-scored file again, or a CLI bug calling apply twice. (e) O(1).

A12Factory function createAchievement

(a) A factory is a function that creates objects for you, choosing the right class from a description, and returns a base-class pointer.

(b)

Achievement* createAchievement(const std::string& type, int id, int studentId,
        const std::string& title, const std::string& date, int score,
        const std::string& proof, const std::string& platform) {
    if (type == "CODING")  return new CodingAchievement(id, studentId, title, date, score, proof, platform);
    if (type == "CERT")    return new CertificateAchievement(...);
    if (type == "OSS")     return new OpenSourceAchievement(...);
    if (type == "INTERN")  return new InternshipAchievement(...);
    return nullptr;                               // unknown type
}

The type strings above match the spec's typeName() values (CODING, CERT, OSS, INTERN); the exact set of accepted strings is my reading of the spec, so check your file.

(c) Used by the CSV loader (the type column) and the CLI (user picks a type). Both get the same logic.

(d) Without it, the loader and the CLI would each have their own copy of the big if chain, and adding a new type would mean editing two places (and forgetting one). One factory means one place. Callers must check for nullptr (unknown type), and the caller (DataStore) takes ownership of the returned pointer.

Part B: ds/LinkedQueue.h (DSA)

B1Queue ADT and FIFO

(a) An ADT (abstract data type) says what operations exist, not how they are built. A queue is a line: add at the rear, remove from the front. FIFO = First In, First Out, like a ticket counter.

(b) Operations: enqueue(x) add at rear; dequeue(out) remove front; peek(out) look at front without removing; isEmpty(); size().

(c) LinkedQueue<int> pending inside VerificationService keeps the ids of Pending achievements in submission order.

(d) Why a queue and not a stack? A stack is LIFO, so the newest submission would be reviewed first and old ones could wait forever. Queue = fairness. Why not a sorted list or priority queue? There is no priority in the spec; fairness by arrival is what we want.

B2Linked list, nodes and pointers; front/rear pointers

(a) A node is a small box holding data plus a pointer (a variable that stores a memory address) to the next node. Nodes chained by pointers form a linked list. nullptr is "points to nothing". A linked queue keeps two pointers: frontNode (oldest) and rearNode (newest).

(b) The spec's layout: Node = { T data; Node* next; }, members Node* frontNode, *rearNode; int count;.

void enqueue(const T& v) {
    Node* n = new Node(v);                  // next = nullptr
    if (rearNode == nullptr) frontNode = rearNode = n;   // queue was empty
    else { rearNode->next = n; rearNode = n; }           // link after old rear, move rear
    ++count;
}
bool dequeue(T& out) {
    if (frontNode == nullptr) return false;              // empty: never touch null
    Node* old = frontNode;
    out = old->data;
    frontNode = frontNode->next;
    if (frontNode == nullptr) rearNode = nullptr;        // became empty
    delete old;  --count;  return true;
}

(c) The whole of ds/LinkedQueue.h.

(d) Why linked, not an array queue? The queue can grow as long as needed with no fixed capacity and no shifting. A circular array is fast too but needs a size limit or resizing, plus careful full/empty logic (front == rear can mean both). Linked cost: extra memory per node for the pointer, and manual new/delete.

B3Why enqueue and dequeue are O(1); other complexities

Enqueue only creates one node and changes rearNode. We never walk the list because rearNode already points at the end. Dequeue only changes frontNode. Neither loops, so the time does not depend on how many items are waiting.

Trap: with only a front pointer, enqueue would need to walk to the end: O(N). The rear pointer is what makes it O(1).

OperationTimeReason
enqueueO(1)rear pointer, no loop
dequeueO(1)front pointer, no loop
peek, isEmpty, sizeO(1)read a pointer or count

B4Empty-queue handling

dequeue(out) returns false when empty and does not touch out's source. It never dereferences a null pointer (which would crash with a segmentation fault). The caller checks the return value. Same for peek. In VerificationService::reviewNext, an empty queue gives nullptr back to the CLI, which prints "nothing pending".

Why bool + out-parameter, not "return a special value like -1"? A template does not know which value is "impossible" for type T. A separate true/false is always unambiguous.

B5Rule of Three / Five: destructor, copy constructor, copy assignment

(a) If a class owns raw memory (calls new), it normally needs three things: a destructor, a copy constructor and a copy assignment operator. (Rule of Five adds the two "move" versions; we do not use them.)

(b) LinkedQueue's destructor frees every remaining node, so no memory leaks when the queue goes out of scope. Its copy constructor and copy assignment are = delete (forbidden):

LinkedQueue(const LinkedQueue&) = delete;
LinkedQueue& operator=(const LinkedQueue&) = delete;

Why forbid copying? The default copy only copies the pointers (a shallow copy). Then two queues share the same nodes:

(c) LinkedQueue (also HashMap and AVLTree delete copies; DynArray chooses to implement a real deep copy instead).

(d) Two good choices: (1) write a deep copy (allocate new nodes), or (2) delete copying. We have no need to copy the review line, so deleting is simplest and turns a possible silent bug into a compile error. This also hits a real mistake: passing a LinkedQueue by value to a function. With copy deleted, the compiler stops you; pass by reference instead.

B6Templates (LinkedQueue<int>)

(a) A template is a code recipe with a blank type. template<class T> class LinkedQueue means "a queue of whatever T you choose". The compiler stamps out a real class for each T you use.

(b) LinkedQueue<int> q; makes a queue of ints. LinkedQueue<std::string> would make one of strings with the same code.

(c) VerificationService uses LinkedQueue<int> pending. Template classes live fully in the header (.h), which is why our files are headers.

(d) Without templates we would copy-paste the same queue for every type, or use void* (loses type safety). Cost: more compile time, and longer error messages. No run-time cost.

Part C: Verification.h

C1VerificationService: submit and reviewNext

(a) The class that connects the queue to the state machine. It owns LinkedQueue<int> pending (ids, FIFO).

void submit(Achievement* a) {
    if (a == nullptr || a->getStatus() != VerificationStatus::Pending) return;  // requires Pending
    pending.enqueue(a->getId());
}

Achievement* reviewNext(const HashMap<int,Achievement*>& registry, bool approve) {
    int id;
    if (!pending.dequeue(id)) return nullptr;            // queue empty
    Achievement* const* slot = registry.find(id);       // const find: O(1), nullptr if unknown
    if (slot == nullptr) return nullptr;                  // unknown id
    Achievement* a = *slot;
    if (approve) a->approve(); else a->reject();         // state machine decides
    return a;
}

The spec says "requires status Pending" for submit but does not say what happens if it is not; the sketch above silently ignores it. Check your real file.

(c) Verification.h. Helpers: peekNextId(int&), pendingCount(), hasPending() (all O(1)).

(e) submit O(1); reviewNext O(1) average (O(1) dequeue + O(1) average hash lookup).

A dangling pointer points to memory that has already been freed (like keeping the address of a house that was demolished). The id is like a roll number: it stays valid, and looking it up in the registry tells you if the student still exists.

C3FIFO is not approval

The queue decides the order of review, nothing else. The first submission is looked at first, but the reviewer can still reject it. reviewNext(registry, approve) takes the decision (approve true/false) from outside, so the verdict is a separate input. Queue = "who is next"; state machine = "what happens to them".

C4VerificationService does not score

reviewNext returns the achievement and stops. The CLI then passes it to RankEngine::applyAchievement(student, ach), which does the maths and calls tryConsumeForScoring(). So: VerificationService never touches EXP; RankEngine never approves or rejects. If the verifier also scored, a bug in one place could break both jobs and be hard to find.

6. Edge cases and honest limitations

SituationWhat the design does
Empty queue on reviewreviewNext returns nullptr; dequeue returns false.
Unknown id in the queue (not in registry)find returns nullptr; reviewNext returns nullptr. The id is already dequeued, so it is dropped.
Approve/reject an already decided itemreturns false, no change.
Apply points twiceblocked by tryConsumeForScoring().
Rejected then approvednot allowed: only Pending can change.
Unknown type string to the factoryreturns nullptr; caller must check it.
Negative scoreweightedPoints multiplies by 0.3 (a softened penalty); the RankEngine keeps the raw score at 0 or above.
Unknown platform for Codingmultiplier 1.0.
Submitting a non-Pending achievementspec says submit requires Pending; so do not queue Approved/Rejected ones.
Copying a LinkedQueuecompile error (copy deleted).

Limitations (say these honestly in the viva)

  • Verification is simulated. There is a reviewer choice (approve true/false) but no real login, no check of the proof link, and no multiple reviewers.
  • No priority. Every submission waits in strict arrival order, even a very important one.
  • No search or removal inside the queue. You cannot cancel one pending item without draining the queue (searching would be O(N)).
  • Not thread-safe. "Check-and-set" protects against repeated calls in one thread, not against two threads at once.
  • Final states. Once Approved or Rejected, an achievement cannot be corrected (no appeal or revoke).
  • Queue is rebuilt on start. Per the spec, Pending items are re-enqueued from the CSV at startup, in file order; the spec does not say the queue itself is saved.
  • protected data is slightly weaker than private.
  • Raw pointers. DataStore must delete each Achievement* exactly once; no smart pointers (unique_ptr is banned).
  • The data is synthetic; this is a prototype, not a production system.

8. Viva questions and model answers

Q1. What is the difference between a class and an object?
A class is a blueprint; an object is one real instance. Achievement describes fields and rules; "achievement 101" is an object.
Q2. What is encapsulation and where do you use it?
Keeping data with its methods and controlling access. The status and pointsApplied fields are protected; outsiders change them only through approve(), reject() and tryConsumeForScoring(), which enforce rules.
Q3. Why use a member-initializer list?
It initialises members directly before the body runs. It is needed for base classes and const/reference members, and it guarantees that status starts Pending and pointsApplied starts false.
Q4. Why inheritance instead of one class with a type field?
Shared data lives once in the base, each type only adds its own behaviour, and a new type needs one new class instead of editing many if/switch blocks. "A CodingAchievement is an Achievement" holds true.
Q5. Why is Achievement abstract? Why pure virtual functions?
A generic achievement has no sensible weight or display, so no default makes sense. = 0 forbids creating it and forces every child to implement display, categoryWeight, typeName; a forgotten one is a compile error, not a silent wrong score.
Q6. What is runtime polymorphism? Show it in your project.
A call through a base pointer runs the derived version, chosen at run time via the vtable. DataStore holds Achievement*; calling categoryWeight() gives 3.5 for Coding and 5.0 for Internship, without any if on the type.
Q7. What does override do? Is it required?
It asks the compiler to check that the function really overrides a base virtual one. It is not required, but it catches typos and a missing const at compile time.
Q8. What if the base destructor is not virtual?
Deleting a derived object through a base pointer would only run the base destructor. That is undefined behaviour; the derived part is not cleaned up. It matters here because DataStore deletes Achievement*.
Q9. platformMultiplier() and basePoints() are virtual but not pure. Why?
They have a sensible default (1.0 and the score). Only types that need something different override them; today only Coding overrides platformMultiplier.
Q10. Why is weightedPoints() non-virtual?
It is the fixed recipe (template-method idea): base points times category weight times platform multiplier, with a 0.3 factor for negative points. Children customise the steps, not the recipe, so no child can break the formula.
Q11. Why enum class instead of a plain enum or int?
Names are scoped (VerificationStatus::Pending), there is no accidental conversion to int, and no name clashes. Ints would be unreadable and accept invalid values.
Q12. Explain your state machine.
Three states: Pending, Approved, Rejected. Only Pending can move, to Approved by approve() or to Rejected by reject(). In any other state those functions return false and change nothing. Approved and Rejected are final.
Q13. How do you stop double points?
Two layers. The state machine stops re-deciding. tryConsumeForScoring() returns true only if Approved and not yet applied, and sets pointsApplied = true in the same function. RankEngine adds EXP only when it returns true, so a second call gives false.
Q14. Why do check and set in one function?
Then the caller cannot do the check and forget the set, or have them separated by other code. The object protects its own rule. It is not thread-safe locking, because this program is single-threaded.
Q15. Why do you have a factory function?
Both the CSV loader and the CLI must make the right derived class from a type string. A single createAchievement avoids duplicated if chains; a new type is added in one place. It returns nullptr for an unknown type.
Q16. What is separation of concerns in your module?
VerificationService only queues and approves or rejects; RankEngine only scores and ranks. Neither does the other's job, which makes testing and debugging easier.
Q17. Why a queue for verification? Why not a stack?
A queue is FIFO, so it is fair: oldest submission first. A stack would review the newest first and could starve old ones.
Q18. Does FIFO mean the first submission is approved?
No. FIFO is only the review order. The reviewer's decision (approve true or false) is a separate input to reviewNext, so the first one can be rejected.
Q19. Why are enqueue and dequeue O(1)?
Enqueue uses rearNode to attach at the end with no walking; dequeue moves frontNode forward. Neither uses a loop. Without a rear pointer, enqueue would be O(N).
Q20. What happens when you dequeue from an empty queue?
It returns false and does not touch any null pointer. reviewNext then returns nullptr, and the CLI reports that nothing is pending.
Q21. In dequeue, why set rearNode = nullptr when the queue becomes empty?
After removing the last node, frontNode is null, but rearNode would still point at the deleted node (dangling). The next enqueue would then link to freed memory. Resetting it keeps the "empty" state consistent.
Q22. Why is copying of LinkedQueue deleted?
A default copy duplicates only the pointers, so two queues share the same nodes and both destructors free them: a double free. We never need to copy the queue, so = delete turns that bug into a compile error. The alternative is a deep copy.
Q23. What is the Rule of Three?
A class that owns raw memory needs a destructor, copy constructor and copy assignment. Our queue has a destructor that frees all nodes, and the two copy operations are deleted.
Q24. Why is LinkedQueue a template? What is LinkedQueue<int>?
A template lets one implementation work for any type; the compiler generates a class for each T. LinkedQueue<int> is a queue of ints, used for achievement ids.
Q25. Why store ids in the queue instead of pointers?
Ids carry no ownership and cannot dangle: if the object is gone, the registry lookup just fails. Pointers raise "who deletes it" and use-after-free risks. The cost is one HashMap lookup, O(1) on average.
Q26. What is the complexity of reviewNext?
O(1) on average: O(1) dequeue plus an average O(1) HashMap lookup, plus O(1) for approve or reject. Space for N pending items is O(N).
Q27. Why did you not use std::queue?
The project constraint is no STL containers, because the goal is to show we understand how the structures work. Building it ourselves also means we handle node memory and edge cases like empty queue and the Rule of Three.
Q28. Why a linked queue and not an array queue?
A linked queue grows with no fixed limit and has O(1) operations. A circular array is also O(1) but needs a capacity (or resizing) and careful full/empty handling. The price of the linked version is a pointer per node and manual delete.
Q29. Can a rejected achievement later be approved?
No. approve() works only from Pending, so it returns false. Rejected is final. Even if it were scored by mistake, tryConsumeForScoring() needs Approved.
Q30. What are the weaknesses of your design?
Verification is simulated, there is no priority or cancel, states are final, the check-and-set is not thread-safe, and the fields are protected rather than private. These are acceptable for a prototype and I can say how I would improve each.
