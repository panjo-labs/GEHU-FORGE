1. The Project in One Page

The problem

A college has hundreds of students. Some win coding contests, some do internships, some contribute to open source, some earn certificates. Today this is scattered: marks sheets, WhatsApp messages, PDFs. There is no single fair list that says "who is doing well, and how well".

GEHU Forge is a C++ program that collects each student's achievements, lets them be verified, turns them into a score (called EXP, from 0 to 10000) and shows a leaderboard (ranking list) of the Top 10.

Why no STL?

STL (Standard Template Library) gives ready-made containers like vector, map, queue. The project rule is: use no STL containers. Only std::string and basic input/output headers are allowed. The goal of this course project is to show that we understand how these structures work inside, so we build them ourselves. (The old version of our code used std::unordered_set and std::vector; the new version uses our own HashSet and DynArray.)

Data and interface

  • 100 synthetic students. "Synthetic" means made-up by our own generator (DataGenerator, seed 2026, so the same data every time). Stored in two CSV files: data/students.csv and data/achievements.csv. If the files are missing, the program generates them.
  • A command-line interface (CLI) – a text menu. You can add a student, submit an achievement, review pending ones, and see the Top 10.
Your two jobs, in one line each (1) User domain model: the classes User and Student that describe who a person is. (2) User interface: class App that talks to the human, checks their input, and calls everyone else's modules.

2. System Architecture and Flow

The flow, step by step (as written in the spec)

  1. Load. DataStore::loadFromCsv() reads data/students.csv and data/achievements.csv (100 synthetic students, seed 2026). If the files are missing, DataGenerator makes the data. (Saksham)
  2. Own. DataStore owns every object. It holds HashMap<int,Student*> and HashMap<int,Achievement*>. (Saksham)
  3. Submit. In the CLI "Submit achievement", App validates the input and builds the object. (Divyanshi)
  4. The new Achievement object starts with status Pending. (Manya)
  5. VerificationService::submit(a) puts its id into a LinkedQueue<int> (first-in-first-out). (Manya)
  6. Review. CLI "Review next" calls VerificationService::reviewNext(registry, approve). (Manya)
  7. Approved → Achievement::approve(); not approved → reject() (a small state machine). (Manya)
  8. RankEngine::applyAchievement(student, ach) runs. (Pranjal)
  9. It first calls ach.tryConsumeForScoring() – a "score only once" guard.
  10. Weighted points = base × categoryWeight × platformMultiplier × dailyDecay.
  11. Raw score → logarithmic normalisation → EXP (0 to 10000).
  12. HashMap erase/update is O(1); AVLTree erase + insert is O(log N).
  13. The AVLTree leaderboard answers getTopK(10) in O(K + log N) and getRank(id) in O(log N).
  14. Show. The CLI prints the leaderboard and the profile card (Student::printProfileCard). (Divyanshi)

3A. The domain model (User.h)

Class vs object

What
A class is a blueprint (like a form design). An object is one filled-in copy (one actual filled form).
How
Student s(...);          // object made from the class blueprint
Student* p = new Student(...);  // object on the heap, pointer p
The class Student says "every student has a name, branch...". The object for "Aarav, CSE" holds the real values.
Where
class Student in User.h. 100 Student objects are created at startup from the CSV (by DataStore); the CLI creates more.
Why
Without classes you would keep separate arrays names[], emails[], branches[] and hope the indices match. One object keeps everything about one student together.

Encapsulation (private fields + getters/setters)

What
Hiding the data inside the class and letting the outside use it only through functions.
How
Like an ATM: you cannot reach into the cash box; you press buttons (functions) that check rules.
// outside code:
s.setGithub("aarav-dev");   // goes through a function
// s.githubHandle = "x";    // ERROR: field is private
Where
All Student fields are private: studentId, branch, graduationYear, githubHandle, leetcodeHandle, skills, achievements. Access is via getters/setters.
Why
If fields were public, any module could set studentId to -5, or replace the achievements list and break the duplicate check. With private fields, only the class's own functions can change data, so rules live in one place. Also, if we later change how skills are stored, outside code does not break. Trade-off: a bit more code to write (getters/setters).

Inheritance: User → Student ("is-a")

What
A new class reuses an existing class. Use it when the sentence "X is a Y" is true: a Student is a User.
How
class User { ... };
class Student : public User { ... };  // Student gets name, email from User
A Student object contains the User part (name, email) plus its own extra fields.
Where
class Student : public User in User.h.
Why
Name and email are not special to students. Any future person type (e.g. Faculty or Admin) would also need them. Put shared parts in User once. The spec only requires Student; do not claim other user types exist in our code.

Abstract class and pure virtual getRole(); runtime polymorphism

What
An abstract class has at least one pure virtual function (written = 0): a promise with no body. You cannot make an object of an abstract class. Polymorphism ("many forms") means the same call does different things depending on the real object.
How
class User {
 public:
  virtual std::string getRole() const = 0;   // no body: must be overridden
  virtual ~User() {}
};
class Student : public User {
 public:
  std::string getRole() const override { return "Student"; }
};
User* u = new Student(...);   // base pointer, derived object
u->getRole();                 // runs Student::getRole at RUN time -> "Student"
// User x(...);               // ERROR: User is abstract
The compiler keeps a hidden table (vtable) per class; at run time the object's table decides which function runs.
Where
User::getRole() pure virtual; Student::getRole() returns "Student".
Why abstract?
A bare "User" with no role is not a meaningful real-world thing. Making it abstract forces every concrete kind of user to declare its role, and prevents creating half-defined users by mistake. Why virtual destructor? If you delete a Student through a User*, a non-virtual destructor would run only ~User() and skip ~Student(), leaking the skills and the pointer list. virtual ~User() fixes this. (The old code also had this virtual destructor.) Honest note: with only one subclass, polymorphism is small here; the design is ready for more roles.

Protected members (name, email)

What
Three access levels: private = only this class; protected = this class and its children; public = everyone.
How
Student code can read name and email directly (for example when printing the card), but main.cpp or App cannot touch s.name; they call getName().
Where
User's name and email.
Why
Children need them; strangers do not. Trade-off: protected data weakens encapsulation a little, because any child class can change it. For two plain strings this is acceptable.

Constructors and member-initializer lists (calling the base constructor)

What
A constructor runs when an object is created and sets its starting values. An initializer list is the part after the colon that sets members while they are being built.
How
Student(int id, std::string name, std::string email, ...)
    : User(name, email),      // 1) build the base part first
      studentId(id), ...      // 2) then our own members
{ }
Order of events: base class constructor first, then members (in the order they are declared in the class), then the body { }. Because User has no default constructor (it needs name and email), the only way to build the base part is to call User(name, email) in this list.
Where
User(name, email) and the Student constructor in User.h.
Why
Without the list, members are first default-constructed and then assigned: double work. Also, const members, references and base classes without a default constructor must use the list; they cannot be assigned later.

The exact parameter list of Student's constructor is not fixed by the spec; check the final User.h and use whatever it says.

Composition ("has-a"): Student HAS-A HashSet and DynArray

What
Composition means one object contains other objects as parts. "A Student has skills", "A Student has achievements".
How
class Student : public User {
  HashSet<std::string>   skills;        // has-a
  DynArray<Achievement*> achievements;  // has-a (non-owning pointers)
};
When a Student object dies, its parts' destructors run automatically.
Where
The private members of Student.
Why composition and not inheritance here?
A Student is not a kind of HashSet. Rule of thumb: use inheritance for "is-a" (Student is a User) and composition for "has-a" (Student has skills). Inheriting from HashSet would expose set functions on Student and mix two ideas. Note that HashSet itself is built by composition on HashMap<T,bool> (Saksham's design): same principle.

Const-correctness: const methods and const& returns

What
A const method promises not to change the object. A const& is a read-only reference: you see the original, no copy is made.
How
std::string getRole() const;                 // does not modify Student
const HashSet<std::string>& getSkills() const; // hand out a read-only view
Returning by value would copy the whole set every call. Returning const& copies nothing, and the caller cannot modify it.
Where
getSkills() const returns a const reference (spec). Also getAchievements() const, printProfileCard(...) const, getRole() const.
Why
(1) Speed: no copy. (2) Safety: the caller cannot change skills behind the class's back (they must use addSkill). (3) A const Student& can only call const methods, so marking getters const lets them work on read-only students. Caution: a reference becomes dangling if the object dies; use it right away and do not store it. And HashSet has no copy constructor (HashMap's is deleted, so the set's copy is not available), which is another reason to return a reference instead of a copy.
Cost
O(1) (no copying).

Non-owning pointers: Student does NOT delete Achievement*

What
An owning pointer is responsible for calling delete. A non-owning pointer just looks at an object someone else owns. Think: a library book (owner = library) and your borrowing card (non-owning).
How
Every Achievement is created with new and handed to DataStore. The DataStore destructor deletes every Student and Achievement. Student::achievements only stores pointers to them. Student's destructor does not delete them.
Where
DynArray<Achievement*> achievements in Student; owner is DataStore (spec: "owns all heap objects").
Why
One owner only. If both Student and DataStore deleted the same achievement, that is a double delete: undefined behaviour, often a crash. Also, VerificationService and the registry hold the same achievements; if a Student deleted them early, those would become dangling pointers. Rule: whoever calls new through the DataStore, DataStore deletes.

linkAchievement: ignores nullptr and duplicates by id

What
Adds an achievement pointer to the student's list, unless it is nullptr or an achievement with the same id is already there.
How
void Student::linkAchievement(Achievement* a) {
    if (a == nullptr) return;                 // factory may give nullptr
    for (int i = 0; i < achievements.size(); i++)
        if (achievements[i]->getId() == a->getId()) return;  // already linked
    achievements.push_back(a);
}
This is an illustration of the behaviour the spec describes. The exact code is in User.h.
Where
Student::linkAchievement; called when loading from CSV and when the CLI submits an achievement.
Why
The factory createAchievement returns nullptr for an unknown type, so a null check prevents a crash. The duplicate check stops the same achievement being counted twice in the profile. The old code (addAchievement) pushed blindly, with only a null check.
Cost
The check is a scan over the student's A achievements: O(A) per link (A is small, 1 to 3 for synthetic students). The push itself is amortised O(1). If a student had thousands of achievements you could use a HashSet<int> of ids for O(1); here it is not needed.

HashSet for skills

What
A set stores each item at most once. HashSet is our own set, built on HashMap<T,bool>. API: add (returns false if already present), contains, remove, size, forEach.
How
Hashing turns the string "C++" into a number, which picks a bucket (a slot). To check "is C++ present?", you only look in that one bucket. Example: 
s.addSkill("C++");   // add -> true
s.addSkill("C++");   // add -> false  (no duplicate stored)
s.hasSkill("DSA");   // contains -> false
Where
Student::skills; addSkill / removeSkill / hasSkill; profile card prints skills with forEach.
Why not an array?
With an array (DynArray), contains and the duplicate check need a scan: O(S). With the hash set: add/contains/remove are average O(1) and duplicates are impossible by design. Worst case (all keys in one bucket) is O(S), but the table rehashes at load factor above 0.75 to avoid that. Trade-off: a set has no order, so skills print in bucket order, not the order typed; and it uses more memory than an array.
Cost
add / contains / remove: avg O(1). Space O(S). Printing all skills: O(S) (plus visiting empty buckets).

HashMap registry: lookup by student id, used by the CLI

What
A map (dictionary) links a key to a value. DataStore keeps HashMap<int,Student*>: student id → Student pointer.
How
HashMap uses separate chaining: each bucket is a linked list of nodes {key, value, next}. find(id) hashes the id, goes to one bucket, walks its short chain. It returns a pointer to the value or nullptr. The CLI uses the wrapper DataStore::findStudent(int):
Student* s = store.findStudent(id);
if (s == nullptr) { std::cout << "No such student id.\n"; return; }
Where
Menu 3 (profile), 5 (submit), 7 (rank). Used to validate "unknown student id" before doing anything.
Why
Searching 100 (or 100,000) students one by one is O(N). The hash map gives average O(1). You do not write the HashMap (Saksham does); you must know how to use it and explain it.

The profile card: printProfileCard

What
Prints one student's details: id, name, email, branch, graduation year, GitHub, LeetCode, skills, achievements, plus the rank, EXP and tier.
How
The caller (App) first gets the three extra numbers from Pranjal's RankEngine: getRank(id) (-1 if unranked), getExp(id), and tierBadge(exp); then calls s->printProfileCard(rank, exp, tier).
Where
Student::printProfileCard(int rank, double exp, const std::string& tier) const. It replaces the old displayProfile().
Why
Rank and EXP are not stored in Student; they belong to RankEngine. So Student receives them as parameters. This keeps one source of truth: if the rank changes, Student has no stale copy. It is const because printing must not change the student.
Cost
O(S + A): S skills printed, A achievements listed. Everything else is O(1). (Same complexity as the old displayProfile.)

3B. The user interface (Cli.h, main.cpp)

Separation of concerns

What
Each module does one kind of job. Like a restaurant: the waiter takes orders, the kitchen cooks, the cashier takes money. The waiter does not cook.
How
App does only input/output and validation. It reads text, checks it, then asks other modules: DataStore stores, VerificationService queues/reviews, RankEngine scores and ranks, Student prints its own card.
Where
class App in Cli.h. It contains no scoring formula and no tree code.
Why
(1) If the scoring formula changes, you do not touch the CLI. (2) The logic can be tested without typing menus (the tests do not need App). (3) Four people can work in parallel. (4) Easy to explain who is responsible for a bug.

Startup flow

What
What the program does before showing the menu.
How
  1. Load the CSVs from data/ (generate with DataGenerator if missing).
  2. Go through every achievement in file order. Each Approved and not-yet-applied achievement is scored through RankEngine::applyAchievement.
  3. Each Pending achievement is enqueued in VerificationService.
  4. Show the menu.
Where
The start-up part of class App (Cli.h).
Why in file order?
The daily-decay rule counts achievements per student per date, in the order they are applied (first 5 per day full value, then 0.4, then 0.1). A fixed order makes the result repeatable: same files → same scores. Rejected ones are neither scored nor queued.
Cost
Scoring N achievements costs about N × O(log students) for the tree updates, plus O(1) hash work each.

The CLI loop and menu

A loop that shows the menu, reads a choice, does it, and repeats until you choose exit.
How

This is a simplified version of App::run() in Cli.h.

Menu as in the spec: 1 Top 10, 2 Top K, 3 Student profile, 4 Add student, 5 Submit achievement, 6 Review next pending, 7 Rank of a student, 8 Dataset statistics, 9 Save, 10 Reset to synthetic seed, 0 Save and exit.
Why
A menu loop is the simplest interface that needs no GUI library, and it matches the course scope.

Top 10 display (menus 1, 2, 7)

What
Shows the best K students and the rank of any student.
How
DynArray<RankKey> top = engine.getTopK(10); gives keys {exp, studentId} already in order (rank 1 first). For each key, App uses findStudent(key.studentId) (O(1)) to get the name, and prints the row. For "Rank of a student", it calls engine.getRank(id); -1 means unranked (the student has no approved scored achievement yet).
Where
App menu items 1, 2, 7 and the profile card.
Why
The sorting work is done once by the AVLTree as scores change, so reading the Top K does not need sorting each time. App only displays.
Cost
getTopK(K): O(K + log N). Name lookups: K × O(1). getRank: O(log N). Total for Top 10: about O(K + log N).

Input validation (why read a whole line, then parse)

What
Validation = checking that input is acceptable before using it. Users type mistakes, and the program must not crash or corrupt data.
How
Spec says the input helpers check: integer range, non-empty text, no commas, unknown student id, unknown type, duplicate. Technique: read the whole line with std::getline, then check/convert it yourself.
Where
The input-helper functions of class App.
Why read a line, not cin >> number?
If the user types abc where a number is expected, cin >> sets a fail flag and leaves abc in the buffer, so a loop can run forever. Mixing cin >> and getline also leaves a leftover newline that makes the next getline return empty. Reading a whole line each time avoids both problems, and lets you say "try again".

Trace (ii): "Submit achievement", then "Review next"

Submit (menu 5).

  1. App asks the student id. findStudent(id); if nullptr: "unknown id", stop.
  2. App asks the type (for example CODING, CERT, OSS, INTERN), title, date (format DD-MM-YYYY), score, proof, and platform. Each is validated (non-empty, no commas, score is an integer).
  3. Id: store.newAchievementId(). Object: createAchievement(type, id, studentId, title, date, score, proof, platform). If it returns nullptr, the type was unknown: report and stop.
  4. The object starts as Pending. App registers it: store.addAchievement(a); student->linkAchievement(a); verification.submit(a) (puts its id at the back of the queue).
  5. Nothing is scored. RankEngine was not called, so the AVLTree and the Top 10 are unchanged.

Review (menu 6).

  1. App asks "approve or reject?" (typically yes/no).
  2. verification.reviewNext(registry, approve). It takes the oldest id from the queue (FIFO), finds the object in the registry in O(1), then calls approve() or reject(), and returns the pointer. It returns nullptr if the queue is empty or the id is unknown; App prints "nothing to review".
  3. If approved: App calls engine.applyAchievement(student, ach). Inside: tryConsumeForScoring() (true only if Approved and not yet applied) → weighted points → EXP → AVLTree erase old key and insert new key. Now the Top 10 can change.
  4. If rejected: no scoring; the Top 10 stays the same.
Worked number (illustration, from the spec's formula) Student submits a CODING achievement on Codeforces, score 1200. Weighted points = 1200 × 3.5 (coding weight) × 2.5 (Codeforces) = 10,500 (first of the day, so decay = 1.0). EXP = 10000 × ln(1 + 10500) / ln(1 + 50000) ≈ 10000 × 9.259 / 10.820 ≈ 8,558 → tier "Master" (≥ 7000).
While Pending, this student's EXP is unchanged. Only after "Approve" does the AVLTree get the new key. If instead you press "Reject", EXP never changes.

Why this design? Unverified claims must not affect the ranking (otherwise anyone could type a big score and top the list). The queue gives fairness (oldest request is reviewed first). The score-once guard makes sure that pressing review twice never double-counts.

5. Edge Cases and Honest Limitations

  • Unranked students: a student with no approved, scored achievement is not in the AVLTree. getRank returns -1; the CLI should show "Unranked", not "-1".
  • Fewer than 10 ranked students: the Top 10 simply shows as many as exist.
  • Empty skills: the profile card must handle zero skills and zero achievements (the old code printed "None listed" / "N/A"; the new card should treat empty in a similar way).
  • Dangling pointers: a const& or an Achievement* must not be used after its owner (DataStore) is destroyed or cleared (clear(), Reset). After Reset, old pointers are invalid; the CLI must re-fetch.
  • Linear duplicate check: linkAchievement scans the student's own list: O(A). Fine for small A.
  • Skills have no order: a hash set does not remember insertion order.
  • No undo: an approved/rejected achievement cannot go back (the state machine allows changes only from Pending).
  • Authentication: there is none. Anyone using the CLI can approve. A real system would need logins and roles. (Role names exist only as getRole().)
  • Text limits: commas are not allowed in free text (CSV limitation); the spec says commas are removed in the CSV writer.
  • Synthetic data: the 100 students are generated, not real; ranks only show that the system works, not real talent.
  • Single user, single thread, console only. No concurrency.
  • Hash worst case: O(1) is average, not guaranteed; a bad hash could put many keys in one bucket.

7. Viva Questions with Model Answers

Tags: conceptdesignedge casetricky. Say answers in your own words; short and calm beats long and memorised.

1 What is the difference between a class and an object?
A class is a blueprint that says what data and functions exist. An object is one real instance made from it, with real values. Student is the class; "Aarav, CSE, 2026" is an object.
2 What is encapsulation?
Keeping data private and allowing access only through member functions, so the class can enforce rules and hide how it stores things.
3 Why not just make all members public? It is less code.
Then any module could put invalid values (like a negative id) or replace the achievements list and break rules such as "no duplicate links". Bugs would be hard to trace because anyone could change anything. With private fields, only Student's functions can change the data. Also we can change the internal storage later without breaking other files.
4 What does inheritance mean, and where do you use it?
A class reuses another class's members. Student : public User: Student gets name and email from User and adds its own fields. Use it for "is-a".
5 Why is User abstract?
A plain "User" with no role is not a complete thing. The pure virtual getRole() forces every real kind of user to say what it is, and the compiler stops anyone from creating a bare User. It is also ready for more roles later.
6 What is a pure virtual function?
A virtual function declared with = 0 and no body in the base class. Derived classes must override it or they are abstract too.
7 What is runtime polymorphism? Show an example from the project.
A call through a base pointer runs the derived version, chosen at run time. User* u = &student; u->getRole(); returns "Student". (Same idea in Manya's Achievement* a; a->display().)
8 Why is the destructor of User virtual?
So that deleting a derived object through a base pointer calls the derived destructor too. Otherwise only ~User() would run and the Student's own members would not be cleaned up (undefined behaviour).
9 What are protected members? Why are name and email protected?
Visible to the class and its derived classes but not to outsiders. Student needs them directly (e.g. to print the card). Outsiders use getters.
10 What does the member-initializer list do in the Student constructor?
It builds the base part and the members during construction: first User(name, email) is called, then Student's own members are initialised. It avoids "default construct then assign". It is mandatory when the base class has no default constructor (User needs name and email), or for const/reference members.
11 In what order are the base constructor, members and body run?
Base class constructor first, then members in the order they are declared in the class (not the order in the list), then the constructor body. Destruction is the reverse.
12 Inheritance or composition: why does Student contain a HashSet instead of inheriting from it?
A Student is not a kind of set; it has skills. Inherit for "is-a" (Student is a User), compose for "has-a" (Student has a HashSet and a DynArray). Inheriting would also expose set operations as if they were Student operations.
13 What is const-correctness?
Marking things const when they should not change. A const method promises not to modify the object, so it can be called on const objects and the compiler catches accidental changes.
14 Why does getSkills() return const&?
It avoids copying the whole set on every call (a copy would be O(S) work, and our HashSet is built on HashMap whose copy is deleted anyway). The const stops callers from changing skills directly; they must use addSkill/removeSkill. Caution: do not keep the reference after the Student is gone.
15 What if Student also deleted its achievements in its destructor?
Double delete. DataStore owns every achievement and deletes them all in its destructor; Student's delete would free them first, then DataStore would free again: undefined behaviour, probably a crash. Other holders (the registry, the verification queue ids) would also point to freed memory. One owner only: DataStore.
16 What is a non-owning pointer?
A pointer that refers to an object but is not responsible for deleting it. Student::achievements holds such pointers.
17 What does linkAchievement guard against, and what is its cost?
It ignores nullptr (the factory returns it for an unknown type) and ignores an achievement whose id is already linked, so nothing is counted twice. The duplicate scan is O(A) for A achievements of that student; the append is amortised O(1).
18 Why a HashSet for skills and not a DynArray?
Add, contains and remove are average O(1) and duplicates cannot exist. A DynArray needs an O(S) scan to check for a duplicate. Trade-off: no order; more memory.
19 What is the worst case of a HashSet operation and how is it avoided?
O(n) if all keys land in one bucket. The underlying HashMap doubles its buckets and re-inserts everything when the load factor (size/buckets) passes 0.75, which keeps chains short.
20 How does the CLI find a student by id, and how fast is it?
Through DataStore::findStudent(id), which uses HashMap<int,Student*>::find: hash the id, go to one bucket, scan a short chain. Average O(1). It returns nullptr when unknown, which the CLI uses to print "no such student".
21 What is the time complexity of printProfileCard?
O(S + A): one pass over S skills and one over A achievements. Rank, EXP and tier arrive as parameters (computed by RankEngine).
22 Why does printProfileCard take rank, exp and tier as parameters instead of Student storing them?
They belong to RankEngine and change whenever any score changes. Storing copies in Student would go stale. Passing them in keeps a single source of truth and keeps Student independent of the ranking code.
23 What is separation of concerns in your CLI?
App only reads input, validates it, calls other modules and prints. Storage is DataStore's job, queueing and review is VerificationService's, scoring and ranking is RankEngine's. So changing the formula needs no CLI change, and each part can be explained and tested on its own.
24 Why validate input at all? The user is just a student.
Any user can mistype. Bad input could crash the program (null pointer for an unknown id), loop forever (non-numeric into cin >>), or corrupt the data file (a comma in a name splits a CSV row). Validation at the boundary keeps the rest of the code safe and simple.
25 Why read a whole line and then parse, instead of cin >> n?
cin >> on bad text sets a fail state and leaves the text in the buffer, which can cause endless loops, and it leaves a newline that breaks the next getline. Reading a full line is predictable: we then check empty, number format, range, commas ourselves and can ask again.
26 Describe what happens at program start.
Load the two CSVs from data/ (generate if missing). Go through achievements in file order: Approved and not-yet-applied ones are scored via RankEngine; Pending ones are enqueued in VerificationService. Then the menu loop starts. File order makes the decay counts, and so the scores, repeatable.
27 A user submits an achievement. Does the Top 10 change at once? Why?
No. It starts as Pending and only goes into the queue. RankEngine is called only after a reviewer approves it via "Review next". So unverified claims cannot affect rankings. A rejected one never affects them.
28 What does getRank return for a student who has no approved achievement?
-1, meaning unranked (the student is not in the AVLTree). The CLI should show a friendly "unranked" message.
29 Why have a --demo mode?
It runs a fixed scripted sequence with no typing. With seeded data it gives the same output every time, so the demo is reproducible, free from typing errors, and quick to re-check after code changes.
30 Why did you replace std::unordered_set and std::vector with HashSet and DynArray? Is yours better?
The project rule is no STL containers, so we show how they work inside. Ours is not "better" than STL (STL is more tested and feature-rich); we have the same core complexities: amortised O(1) append, average O(1) set operations. Our versions are simpler and we can explain every line.
31 What are the weaknesses of your design?
No login (anyone can approve), no undo, console only, commas not allowed in text, skills are unordered, duplicate-link check is linear in a student's achievements, data is synthetic. Being honest about these is expected.
